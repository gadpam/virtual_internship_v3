ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Утренний инцидент: отчёт в 1С и цифра на витрине разошлись, бизнес ждёт ответа
«где правда». Открывать документы по одному — час, а нужен ответ за десять минут.
Сегодня учимся смотреть данные там, где они физически лежат.

Язык запросов 1С прячет от вас таблицы СУБД, и это правильно для разработки.
Но проверять данные, искать расхождения и разбирать инциденты без прямого чтения
базы невозможно. Глубокий уровень СУБД - планы, индексы, блокировки - будет в
sprint_31-33. Здесь минимум: подключиться к PostgreSQL из Docker-окружения,
прочитать данные тремя конструкциями и понять, где прямой SQL уместен, а где запрещён.

ТЕОРИЯ: что нужно знать перед выполнением
PostgreSQL стенда хранит не базу 1С, а витрины хаба (схема marts): измерения
dim_store/dim_product/dim_date и факт fact_sales. Инициализация контейнера
выполняет SQL из tools/sql/marts/ при первом старте тома. Подключение: psql
внутри контейнера postgres или любой GUI-клиент на localhost:5432, доступы — в .env.

Базовый SELECT: SELECT колонки FROM таблица WHERE условие ORDER BY сортировка
LIMIT количество. WHERE фильтрует строки до группировки; ORDER BY без LIMIT на
большой таблице — дорогая сортировка всего набора. Агрегаты (SUM, COUNT, AVG,
MIN, MAX) с GROUP BY сворачивают строки в группы: «выручка по магазинам» — это
SUM(revenue) + GROUP BY store. HAVING фильтрует уже группы, а не исходные строки.

JOIN соединяет таблицы по ключу: INNER JOIN оставляет только совпавшие пары,
LEFT JOIN — все строки левой таблицы и NULL справа при отсутствии пары. Витрина
v_sales_daily уже содержит готовое соединение факта с измерениями: сверяя свой
GROUP BY с итогом представления, вы проверяете себя вторым независимым способом.

Таблицы самой информационной базы 1С устроены иначе: платформа генерирует имена
вида _Reference103 (справочник), _Document123 (документ), поля ссылок хранятся
с суффиксами _IDRRef и типом. У файловой ИБ всё это внутри файла .1CD; у серверной —
в отдельной базе СУБД, которую создаёт сервер 1С. Подробно — в task_181 (Q3).
Прямой SQL по таблицам 1С допустим только на чтение: запись мимо платформы ломает
ссылочную целостность, итоги регистров и механизмы обменов.

Пример проверочного запроса из задания: SELECT s.store_code, SUM(f.revenue)
FROM marts.fact_sales f JOIN marts.dim_store s ON s.store_key = f.store_key
GROUP BY s.store_code ORDER BY 2 DESC LIMIT 5. Если итог по всем магазинам из
этого запроса не сошёлся с SUM(revenue) без группировки — ищите строки факта,
у которых store_key не нашёлся в измерении (при INNER JOIN они молча выпадают).
Типичная ошибка: делать выводы по витрине, не посмотрев, каким SQL она наполняется:
у стенда fact_sales генерируется случайно, поэтому «странные» цифры в ней —
не инцидент, а учебные данные.

ЗАДАНИЕ: что сделать
1. Подключитесь к PostgreSQL стенда (база rih из docker compose: psql в контейнере
   postgres или DBeaver; доступы — в вашем .env). Таблицы витрин создаёт
   инициализация контейнера из internship/tools/sql/marts/. Перечислите таблицы
   и посчитайте строки в трёх самых крупных.
2. Выполните SELECT с WHERE, ORDER BY и LIMIT по витрине продаж: например, топ
   магазинов по сумме за период. Сохраните запрос и результат.
3. Выполните JOIN двух таблиц и GROUP BY с агрегатом: количество строк и сумму в
   разрезе групп. Сверьте одну цифру вторым способом внутри той же базы: итог
   SUM(revenue) по marts.fact_sales за период против того же итога из представления
   marts.v_sales_daily. Цифры обязаны сойтись; если нет — найдите и объясните
   расхождение. Отдельно посчитайте итог planned_quantity по CSV
   (internship/data/sales_plan_sample.csv) и письменно объясните, почему с витриной
   он не сверяется: CSV — план продаж, а витрина — факт, и данные факта стенд
   генерирует сам.
4. Ответьте письменно в рефлексии: где физически лежат таблицы самой информационной
   базы 1С (_ReferenceNN и подобные)? Если ваша RIH_DEV файловая — почему её таблиц
   нет в PostgreSQL стенда и что должно стоять между платформой и СУБД в серверном
   варианте. Таблицы серверной ИБ разберём в task_181.
5. Найдите одно подозрительное место в данных (дубль, пустой ключ, отрицательная
   сумма) и опишите, как проверили, не изменяя данные. Запишите правило проекта:
   когда прямой SQL допустим (чтение, диагностика, учебный стенд), а когда запрещён
   (запись в таблицы 1С, обход прав, продуктив без согласования).
