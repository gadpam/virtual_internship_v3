ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
У ментора стенд поднялся одной командой, у вас — нет. Фраза «у меня работает»
в команде не аргумент: окружение должно описываться кодом и подниматься
одинаково у стажёра, ментора и в CI.

База в task_0 уже поднята через Docker, но пока это «одна команда по инструкции».
В команде так не работают: окружение должно подниматься одинаково у вас, у ментора
и в CI. docker compose описывает сервисы, тома, сети и порты одним файлом, и
расхождение «у меня работало» превращается в видимый дифф конфигурации.
Стенды командного уровня будут в sprint_44; здесь - рабочий минимум.

ТЕОРИЯ: что нужно знать перед выполнением
Docker решает задачу «одинаковое окружение у всех». Образ — неизменяемый шаблон
файловой системы и команды запуска, собранный слоями. Контейнер — изолированный
процесс из образа со своим сетевым пространством. Том (volume) — именованное
хранилище вне контейнера: удалили контейнер — данные в томе остались. Команда
docker compose down удаляет контейнеры, но не тома; down -v удаляет и тома — это
уже уничтожение данных.

Файл docker-compose.yml описывает сервисы стенда декларативно: образ, порты,
тома, сеть, переменные окружения, healthcheck (проверка «сервис жив и готов»).
Переменные подставляются из .env по правилам: ${VAR:-значение} — если не задана,
взять значение по умолчанию; ${VAR:?ошибка} — если не задана, не стартовать вовсе.
Так в стенде задан пароль PostgreSQL: compose честно упадёт без .env, а не поднимет
СУБД с паролем «по умолчанию».

Публикация порта «${POSTGRES_PORT:-5432}:5432» означает: на хосте слушаем 5432
и пробрасываем в контейнер. Внутри docker-сети сервисы ходят друг к другу по именам
(postgres:5432) без публикации. Поэтому смена POSTGRES_PORT меняет только внешний
доступ, а POSTGRES_DB срабатывает лишь при первой инициализации пустого тома:
база в уже созданном томе от переименования переменной не пересоздастся.

Назначение каждого сервиса RIH вы разбираете в задании: PostgreSQL — данные
витрин и (для серверной ИБ) база 1С; RabbitMQ — очередь обменов; mock-* — учебные
«внешние системы»; nginx — единая точка входа; ai_service — Python-сервис Q4.

Пример проверки подстановки: команда docker compose config показывает итоговый
конфиг сервиса с уже подставленными значениями из .env — так проверяют, что
compose видит именно ваш пароль и порт, а не значения по умолчанию. В логах
postgres готовность выглядит строкой «database system is ready to accept
connections»; пока её нет, 1С будет честно получать отказ в соединении, и это
не «сломался Docker», а сервис ещё не поднялся. Типичная ошибка: держать данные
в контейнере без тома — первый же пересоздавшийся контейнер уносит базу с собой.

ЗАДАНИЕ: что сделать
1. Разберите internship/tools/docker-compose.yml: сервисы, образы, тома, сети,
   порты, переменные окружения. Для каждого сервиса запишите, зачем он нужен RIH.
2. Убедитесь, что `.env` создан из шаблона `.env.example` (вы делали это в
   task_0; если файла нет — `cp .env.example .env`: без него compose не стартует,
   POSTGRES_PASSWORD обязателен). Остановите окружение (docker compose down) и
   поднимите заново одной командой docker compose up -d. Проверьте:
   docker compose ps, логи СУБД, подключение 1С.
3. Измените один параметр через .env (например, NGINX_HTTP_PORT или
   POSTGRES_PORT), пересоздайте сервис и покажите, что код и compose-файл при
   этом не менялись. Имя базы через .env на уже созданном томе не переименуете:
   POSTGRES_DB применяется только при первой инициализации тома.
4. Намеренно сломайте окружение: остановите контейнер СУБД и зафиксируйте, какую
   ошибку видит 1С. Восстановите окружение и запишите диагностику в рефлексию.
5. Запишите в internship/tools/VERSIONS.md версии Docker и используемых образов.

РЕЗУЛЬТАТ (Definition of Done):
- Окружение поднимается одной командой с чистого состояния; есть вывод ps и логов
- Для каждого сервиса compose записано его назначение
- Параметр изменён через .env без правки compose-файла
- Учебная поломка диагностирована и восстановлена; версии зафиксированы в VERSIONS.md

ПОДСКАЗКИ МЕНТОРА:
- Не храните секреты в compose-файле: только через .env и переменные окружения. Настоящие секреты и их ротация - тема task_261.
- Данные живут в томах (volumes), а не в контейнере. Команда down -v удаляет данные: на учебном стенде это способ начать с нуля, на командном - инцидент.
