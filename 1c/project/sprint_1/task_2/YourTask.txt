ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Вчера вы сохранили файл Rih.cf. Сегодня тимлид просит показать одной ссылкой,
что именно изменилось в модуле, — а не бинарным файлом по почте. Чтобы правки
можно было ревьюить, конфигурация должна лежать в Git текстом.

Чтобы положить конфигурацию в Git, её надо превратить в набор текстовых
файлов. Есть два пути: выгрузка «в файлы» средствами конфигуратора/EDT и проектная
структура EDT (Configuration.xml + папки Catalogs, Documents, Reports и т.д.).
Мы работаем по второму пути: он даёт стабильные диффы и возможность ревьюить код.

ТЕОРИЯ: что нужно знать перед выполнением
Проект EDT раскладывает конфигурацию по папкам классов метаданных: Catalogs,
Documents, CommonModules, DataProcessors, Roles, Subsystems и т.д. Каждый объект —
своя папка: файл <ИмяОбъекта>.xml описывает свойства (реквизиты, типы, права),
а Module.bsl содержит программный код. Корень — src/Configuration/Configuration.xml:
имя и состав конфигурации. Такое разложение даёт стабильные текстовые диффы: правка
одного реквизита меняет несколько строк в одном XML, а не весь бинарный файл.

Код 1С исполняется в разных контекстах: на сервере (кластер 1С, доступ к данным),
на клиенте (интерфейс пользователя), во внешнем соединении. Директивы компиляции
&НаКлиенте, &НаСервере, &НаСервереБезКонтекста указывают, где метод доступен.
Общий модуль своими флагами (Сервер, Клиент, Вызов сервера) определяет, откуда его
методы можно вызывать. Серверный модуль не может показать сообщение пользователю:
Сообщить() — клиентская операция. Правильный приём: серверная экспортная функция
возвращает данные (строку, структуру), а клиентский код — внешняя обработка или
форма — выводит их через Сообщить(). Именно так устроена ПроверитьОкружение().

Вызов серверной процедуры с клиента идёт через флаг «Вызов сервера» общего модуля:
клиент вызывает метод как обычный, платформа сама делает сетевой переход. Каждый
такой переход стоит времени, поэтому серверные вызовы из форм делают редкими и
возвращают всё нужное одним пакетом.

Git видит только текст: файлы Module.bsl в UTF-8 с переводами строк LF. Если
core.autocrlf не равен false, Windows-конвертация CRLF сделает «изменённым» весь
файл в каждом коммите и убьёт ревью. Поэтому первый git diff в задании — не
формальность, а проверка, что ваш инструмент пишет ровно те строки, что вы меняли.

Пример диффа, который вы должны увидеть в задании: изменили одну строку в
Module.bsl — git diff показывает одну красную и одну зелёную строку. Если вместо
этого «изменён весь файл», ищите переводы строк или кодировку, а не «глюк Git».
Пример границы контекстов: функция СведенияОбОкружении() в стартовом модуле
использует Метаданные и ТекущаяДатаСеанса() — это серверные возможности, на тонком
клиенте их нет; поэтому отчёт об окружении собирает сервер, а клиент только
показывает готовую строку пользователю.

ЗАДАНИЕ: что сделать
1. Изучите структуру папки `internship/Configuration/src/`: найдите
   Configuration/Configuration.xml и папки CommonModules, Catalogs, Documents,
   DataProcessors, Roles, Subsystems.
2. Откройте один общий модуль и посмотрите, как выглядит исходник: файл Module.bsl.
3. В общем модуле `РИХ_ОбщегоНазначения` уже есть экспортная функция
   `ПроверитьОкружение()` — разберите её. Модуль серверный, поэтому функция не
   вызывает `Сообщить()`, а возвращает текст отчёта: сообщение пользователю
   показывает вызывающий код на клиенте. Доработайте функцию: добавьте в отчёт
   строку соединения информационной базы и имя текущего пользователя.
4. Обновите конфигурацию базы RIH_DEV и вызовите функцию с клиента: временной
   внешней обработкой (форма с кнопкой: `Сообщить(РИХ_ОбщегоНазначения.ПроверитьОкружение())`)
   или через представление «Выражения» в отладке EDT. Обработку в Git не коммитим.
5. Посмотрите `git diff` и убедитесь, что видно ровно вашу правку и ничего лишнего.

РЕЗУЛЬТАТ (Definition of Done):
- Изменение видно в git diff как несколько строк текста, а не как «изменён бинарный файл»
- Функция вызвана с клиента, текст отчёта показан пользователю (Сообщить во внешней обработке)
- В рефлексии описано, из каких папок состоит проект EDT и где живёт код модуля
- Конфигурация обновилась без ошибок и предупреждений

ПОДСКАЗКИ МЕНТОРА:
- Префикс РИХ_ (Retail Integration Hub) — соглашение именования подсистемы. Оно понадобится в task_6 и будет проверяться на code review.
- Если git diff показывает «файл изменён целиком», проверьте кодировку и переводы строк: core.autocrlf должен быть false, файлы — UTF-8.
- Module.bsl — обычный текст, его можно открывать в любом редакторе, но правьте всё-таки через EDT, чтобы не потерять метаданные.
