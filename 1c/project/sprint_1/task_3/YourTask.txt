ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
В команде уже теряли чужую правку: два разработчика одновременно трогали один
модуль, и одна из версий молча перезаписала другую. Решение ментора: «С сегодня
все изменения — только ветками и атомарными коммитами, как в обычной разработке».

В 1С-команде Git — это не только хранение кода, но и способ выжить при
параллельной разработке: несколько человек правят одну конфигурацию, обновления
типовых приходят каждые две недели, а релиз надо выпускать в окно ночью в субботу.
Без дисциплины коммитов и веток такая команда тонет в конфликтах.

ТЕОРИЯ: что нужно знать перед выполнением
Git хранит не «изменения файлов», а снимки состояния (коммиты). Коммит = дерево
файлов + родитель + автор + сообщение. Ветка — просто подвижный указатель на коммит.
Рабочий каталог — файлы на диске; индекс (staging) — то, что попадёт в следующий
коммит; HEAD — текущий коммит. Три атомарных коммита в задании — это дисциплина:
один коммит решает одну задачу, его можно откатить и заревьюить отдельно.

Слияние (merge) объединяет две линии истории. Если ветки не трогали одни и те же
строки, Git справится сам. Если трогали — конфликт: файл получает маркеры
<<<<<<< HEAD / ======= / >>>>>>>, и человек выбирает итоговый текст. После ручного
разрешения обязательны коммит слияния и проверка, что код работает: в 1С конфликт
особенно опасен, потому что слияние XML метаданных может молча потерять реквизит.

Файл .gitignore перечисляет то, что в репозиторий не попадает: бинарные артефакты
1С (*.cf, *.cfu, *.dt), логи, локальные настройки (Service/), секреты (.env).
Правило добавляют один раз на команду, а не каждый под себя.

Хранилище конфигурации 1С — штатный предшественник Git в мире 1С: объекты
«захватываются» одним разработчиком (пессимистичная блокировка), правятся и
«помещаются» обратно с номером версии. Плюсы: нативно понимает метаданные.
Минусы против Git: нет нормальных веток и ревью по диффам, слабая работа офлайн,
нет CI. Поэтому современные команды ведут исходники в Git (структура EDT),
а хранилище остаётся для легаси-контуров.

Пример конфликта: вы и «вторая ветка» изменили приветствие в одном модуле.
Git остановит слияние и оставит в файле блок с маркерами <<<<<<< и >>>>>>>.
Ваша работа — не «выбрать свою половину», а собрать итоговый текст, который
сохраняет обе правки, убрать маркеры, обновить конфигурацию базы и только потом
коммитить слияние. Команда git log --oneline --graph покажет, как ветки разошлись
и сошлись, — этот график ментор попросит на ревью. Типичная ошибка: коммит
«правки» из десяти файлов по трём задачам — его невозможно ни откатить точечно,
ни объяснить через полгода.

ПОДСКАЗКИ МЕНТОРА:
- Конфликты в 1С опаснее, чем в Java: можно тихо потерять реквизит объекта. Поэтому после любого слияния — обновление ИБ и дымовой прогон.
- Сообщение коммита «правки» — это технический долг. Пишите так, чтобы через полгода понять, зачем это было.
- Проверьте git log --stat: видно, какие именно файлы менялись.
