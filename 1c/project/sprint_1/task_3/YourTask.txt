ЗАДАНИЕ task_3 · спринт 1 · Q1
Тема спринта: Инструменты разработки: Конфигуратор, EDT, Git, Docker, Python-минимум
Git и хранилище конфигурации: ветки, коммиты, захваты объектов

Оценка времени: 2 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

КОНТЕКСТ: зачем это нужно
В 1С-команде Git — это не только хранение кода, но и способ выжить при
параллельной разработке: несколько человек правят одну конфигурацию, обновления
типовых приходят каждые две недели, а релиз надо выпускать в окно ночью в субботу.
Без дисциплины коммитов и веток такая команда тонет в конфликтах.

ЗАДАНИЕ: что сделать
1. Изучите `.gitignore` в корне репозитория: часть правил там уже есть. Добавьте
   недостающие для артефактов 1С: *.cf, *.cfu, *.dt, Service/ (локальные
   настройки), *.log.
2. Создайте ветку `trainee/<ваше-имя>/task_3` и переключитесь в неё.
3. Сделайте три атомарных коммита: (а) .gitignore, (б) правка модуля из task_2,
   (в) рефлексия. Сообщения в формате «task_N: что сделано».
4. Попробуйте намеренно изменить одну и ту же строку общего модуля в двух ветках
   и выполнить слияние. Разрешите конфликт вручную.
5. Опишите в рефлексии, как вы поняли, какую строку оставить.
6. Сравните Git и хранилище конфигурации по 5 критериям: захваты объектов, диффы
   и ревью, работа офлайн, CI, разрешение конфликтов. Своими словами опишите
   жизненный цикл правки в хранилище: подключение, захват, правка, помещение,
   отмена захвата. Зафиксируйте в internship/tools/VERSIONS.md версии платформы,
   СУБД, EDT и минимальную версию платформы проекта.

- В рефлексии описан алгоритм разрешения конфликта в конфигурации
- Есть таблица «хранилище vs Git» (5 критериев) и версии инструментов в VERSIONS.md

ПОДСКАЗКИ МЕНТОРА:
- Конфликты в 1С опаснее, чем в Java: можно тихо потерять реквизит объекта. Поэтому после любого слияния — обновление ИБ и дымовой прогон.
- Сообщение коммита «правки» — это технический долг. Пишите так, чтобы через полгода понять, зачем это было.
- Проверьте git log --stat: видно, какие именно файлы менялись.
