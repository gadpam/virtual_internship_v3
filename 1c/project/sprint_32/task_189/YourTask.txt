ЗАДАНИЕ task_189 · спринт 32 · Q3
Тема спринта: Планы запросов, индексы, статистика: глубокая оптимизация
Статистика и параметризация: почему план «прыгает»

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Запрос вчера летал, сегодня ползёт, код не менялся. Виновник часто —
план, построенный под первое значение параметра. Сегодня разбираемся
в parameter sniffing и устаревшей статистике.

Один и тот же запрос с разными параметрами может выполняться по-разному:
план строится по первому значению параметра (parameter sniffing), а статистика
устаревает. Результат — «утром быстро, вечером медленно».

ТЕОРИЯ: что нужно знать перед выполнением
Оптимизатор строит план по статистике распределения данных и — при
параметризованном запросе — по значению параметра первого выполнения
(parameter sniffing): для значения «10 строк» выбран Nested Loops,
план закэширован, а запросу с «500 000 строк» нужен Hash Join.
Симптом: «одному пользователю быстро, другому медленно» при одном
запросе — диагностируется сравнением планов для разных параметров.

Статистика — гистограммы распределения; устаревшая статистика
(после массовой загрузки) даёт оптимизатору неверные оценки строк,
и планы «прыгают». Обновление статистики чинит оценки, но может
поменять планы всей системы: делается осознанно, в окно, с контролем
ключевых запросов после.

Лечение sniffing-а: OPTIMIZE FOR (план под указанное/неизвестное
значение), локальная переменная (оптимизатор не знает значения —
строит «средний» план), принудительный план/перекомпиляция, разделение
запроса на ветки по объёму. У каждого — цена; два способа из задания
проверяются на учебном примере замерами.

В 1С параметризация штатна, поэтому проблема приходит с большими
отчётами и «неудачным» первым запуском после перезапуска сервера.

Учебный пример: параметр «склад» — РЦ даёт 400 000 строк, филиал —
12; план, построенный под филиал, для РЦ работает в 60 раз дольше.
Типичные ошибки: лечить «перезапуском сервера» (помогает до первого
неудачного запуска); статистику обновлять ночью всей базы без
контроля ключевых запросов утром; чек-лист писать «обновите
статистику» без симптомов, по которым узнают болезнь.

ЗАДАНИЕ: что сделать
1. Продемонстрируйте parameter sniffing на учебном примере: запрос с параметром,
   где одно значение даёт 10 строк, другое — 500 000.
2. Сравните планы для «малого» и «большого» значения параметра.
3. Разберите способы лечения: OPTIMIZE FOR, локальная переменная, пересбор плана,
   разделение запроса.
4. Проверьте актуальность статистики на своей базе и обновите её; оцените эффект.
5. Опишите симптом и диагностику в чек-лист «план прыгает: что делать».

РЕЗУЛЬТАТ (Definition of Done):
- Parameter sniffing продемонстрирован с двумя планами
- Минимум два способа лечения проверены на практике
- Статистика обновлена, эффект оценён
- Чек-лист диагностики сохранён

ПОДСКАЗКИ МЕНТОРА:
- В 1С параметризация запросов штатная, поэтому проблема проявляется на больших отчётах с «неудачным» первым запуском.
- Обновление статистики может резко изменить планы всей системы. Делайте это осознанно и в окно обслуживания.
