ЗАДАНИЕ task_80 · спринт 14 · Q2
Тема спринта: HTTP-сервисы в 1С: публикуем свой API
XDTO-модели и сериализация: структура вместо «строки на глаз»

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Ответ сервиса собирали «строкой на глаз» — и первое же наименование
с кавычкой развалило JSON партнёру. Сегодня сериализация получает
схему: XDTO-пакет описывает типы один раз, а платформа проверяет
данные по ней до вашего кода.

XDTO — механизм описания структур данных в 1С с типами, фацетами и
сериализацией в XML/JSON. Использовать его в интеграциях правильно: схема проверяет
данные, а документация получается из модели, а не из переписки.

ТЕОРИЯ: что нужно знать перед выполнением
XDTO — механизм описания структур в конфигурации: пакет XDTO задаёт
типы объектов и значений, их свойства, обязательность и фацеты
(длина строки, диапазон числа, список допустимых значений). По пакету
платформа строит объекты, сериализует их в XML и JSON и — главное —
проверяет входящие данные по схеме до бизнес-логики.

Пакет РИХ.Обмен.1 из задания описывает контракт HTTP-сервиса
(task_79/83): Продукт, Заказ, ПозицияЗаказа, ОтветОшибки. Типы XDTO
и схемы OpenAPI (task_77) — два представления одного контракта;
расхождение между ними — дефект, а не «так получилось».

Пространство имён пакета — часть идентичности типов: одинаковые
имена в разных пространствах — разные типы, и фабрика XDTO их
не смешает. Версия живёт в имени пакета (РИХ.Обмен.1): ломающее
изменение контракта — новый пакет рядом со старым, потребители
переезжают по одному, как версии API в task_82.

Сериализация дат и чисел задаётся типами пакета явно: дата без зоны
и число «как получилось» на стыке превращаются в расхождения,
которые ищут днями. Вложенные объекты (заказ с позициями) описываются
композицией типов, а не строками «через разделитель».

XDTO даёт структуру, проверяемую платформой до вашего кода:
невалидный пакет падает на границе с понятной причиной, а не
внутри обработки с «поле не найдено». Пакеты XDTO версионируются
вместе с контрактом: поле добавили — совместимость проверили
на старом потребителе. Преобразование «XDTO ↔ структуры данных»
живёт в одном месте сервиса: размазанная по обработчикам
сериализация гарантирует три разных формата одного документа.
Для простых плоских обменов JSON честнее: XDTO оправдан
сложной вложенной структурой и строгой схемой.

ЗАДАНИЕ: что сделать
1. Создайте XDTO-пакет `РИХ.Обмен.1` с типами: Продукт, Заказ, ПозицияЗаказа,
   ОтветОшибки.
2. Реализуйте сериализацию документа «Поступление товаров» в XDTO-объект и в JSON.
3. Реализуйте десериализацию входящего JSON в XDTO и проверку по схеме.
4. Сравните подход «XDTO» и «Структура + ручная сборка JSON» по 5 критериям (надёжность,
   документирование, скорость разработки, производительность, изменения контракта).
5. Переведите один из маршрутов task_79 на XDTO.

РЕЗУЛЬТАТ (Definition of Done):

- Сериализация и десериализация работают на реальных данных

- Сравнение подходов оформлено таблицей

ПОДСКАЗКИ МЕНТОРА:
- XDTO окупается на стабильных контрактах и сложных структурах. Для «одного поля» он избыточен — но правило лучше установить сразу.
- Проверка по схеме ловит то, что вы никогда не поймаете вручную: лишние поля, неверные типы, пропущенные обязательные.
