Первый HTTP-сервис в 1С: маршруты и публикация

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Партнёрам неудобно слать файлы: «Дайте адрес, куда стучаться за ценами».
Сегодня RIH впервые становится сервером: публикуем HTTP-сервисы конфигурации
и проверяем их, как внешние клиенты.

HTTP-сервис в 1С — это объект конфигурации с шаблонами URL и методами.
После публикации на веб-сервере он становится доступен извне. Здесь отрабатывается
вся цепочка: конфигурация → публикация → веб-сервер → запрос → ответ.

ТЕОРИЯ: что нужно знать перед выполнением
HTTP-сервис 1С — объект конфигурации: корневой URL, шаблоны URL с методами,
обработчики в модуле сервиса. Платформа сама принимает HTTP, вызывает
обработчик с объектом HTTPСервисЗапрос и ждёт HTTPСервисОтвет: код, заголовки,
тело (строка или двоичные данные). Публикация — веб-сервер с модулем
расширения платформы: файл публикации описывает, какие сервисы видны наружу;
без публикации сервис существует только в Конфигураторе. Nginx стенда —
обратный прокси перед веб-сервером платформы, а не сам сервер 1С.

Контракт сервиса — это его ответы на все случаи: товар найден (200 + JSON
товара), не найден (404 + JSON ошибки единого формата), битый запрос
(400 с указанием поля). Ошибку оформляют машиночитаемо (code, message,
details), а не HTML-страницей веб-сервера.

Авторизация учебных сервисов: сначала открыто на локальном стенде,
затем — заголовок с ключом (проверка первым блоком обработчика); настоящее
разграничение прав позже дают роли платформы и task_120–124 про JWT.
Проверяют сервисы из Postman коллекцией (task_76): свой сервис тестируют
теми же инструментами, что чужие.

Переделывать «в лоб» внутренние процедуры в сервис нельзя: сервис — тонкий
адаптер (разобрал запрос → вызвал прикладной общий модуль → упаковал
ответ), логика живёт в модулях и тестируется без HTTP.

Проверочный набор сервиса из трёх запросов: существующий товар (200
и тело сверено с карточкой), несуществующий (404, формат ошибки),
битый параметр (400 с полем). Типичные ошибки: обработчик тянет
логику в модуль сервиса (сервис толстеет, тесты плачут); ошибка
платформы наружу 500-й страницей веб-сервера вместо JSON-контракта;
авторизацию отложить «на потом» и забыть пункт в гайде task_89;
тестировать только из Конфигуратора (настоящая проверка — снаружи,
через публикацию, как партнёр). Схема публикации — часть инструкции
администратора из task_66.

Публикация сервиса начинается с маршрутов и публикации веб-сервера,
а понимание проверяется снаружи: запрос с другой машины, а не
«у меня в тонком клиенте работает». Разделяйте ошибки маршрутизации
(404 — нет такого пути), метода (405), авторизации (401/403)
и бизнес-ошибки: смешение классов делает отладку потребителя
угадайкой. Базовая проверка живности (/health) не должна ходить
в базу глубоко — иначе healthcheck сам становится нагрузкой
и источником ложной «мертвости» сервиса.

ЗАДАНИЕ: что сделать
1. Создайте HTTP-сервис `РИХ_Обмен` с маршрутом GET /health, возвращающим
   статус, версию конфигурации и время сервера.
2. Опубликуйте конфигурацию на веб-сервере и проверьте доступ из Postman.
   Нужен веб-сервер с модулем расширения 1С (Apache/IIS, штатная публикация
   из Конфигуратора); nginx стенда при этом — обратный прокси перед ним,
   сам по себе HTTP-сервисы 1С он не отдаёт.
3. Добавьте маршрут GET /products с параметрами: группа, дата изменения, лимит, смещение.
4. Реализуйте пагинацию и возврат списка товаров в JSON.
5. Зафиксируйте в документации: URL, порты, как перепубликовать после изменений.

РЕЗУЛЬТАТ (Definition of Done):
- GET /health отвечает 200 с JSON-статусом
- GET /products возвращает данные с пагинацией (проверено на 1000 товаров)
- Сервис опубликован и доступен из Postman
- Инструкция по публикации сохранена

ПОДСКАЗКИ МЕНТОРА:
- Частая проблема: сервис работает в конфигураторе, но не отвечает извне. Проверяйте публикацию, права пользователя веб-сервера и порты.
- Пагинация обязательна: без неё первый же запрос «все товары» положит сервис.
