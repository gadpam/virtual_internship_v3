ЗАДАНИЕ task_83 · спринт 14 · Q2
Тема спринта: HTTP-сервисы в 1С: публикуем свой API
POST/PUT/DELETE: приём заказов от онлайн-магазина

Оценка времени: 4 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Магазин готов слать заказы завтра. Один заказ — товар, количество, цена,
статус. Принять его надо так, чтобы повторная отправка не родила второй
документ, а кривой заказ не лёг молча. Сегодня рождается главный документ Q2.

Основной сценарий RIH: онлайн-магазин присылает заказы, 1С их принимает,
создаёт документы, возвращает результат. Здесь появляются все классические проблемы:
дубли, частичные данные, конфликт состояний, атомарность приёма нескольких заказов.

ТЕОРИЯ: что нужно знать перед выполнением
HTTP-сервис приёма (task_79) получает JSON заказа и создаёт документ
ЗаказКлиента: номер, дата, контрагент, магазин, табличная часть, статус.
Документ вводит регистр ЗаказыКлиентов (приход количества и суммы),
чтобы статусы и итоги жили запросом, а не пересчётом документов в цикле.

Идемпотентность — центральное свойство задания: у документа реквизит
ВнешнийИдентификатор (externalId магазина). Приём сначала ищет заказ по
externalId: нашёлся — вернуть его номер и статус 200/409 по контракту,
а не создавать дубль. Уникальность страхуется на уровне данных: два
параллельных запроса с одним externalId не должны пройти оба (контроль
в транзакции документа — отсылка к task_44/45).

Валидация платежа/статуса: заказ принимается в известных статусах
перечисления, цена и количество > 0, товар сопоставлен (task_39);
несопоставленный товар — 422 с указанием позиции, а не «приняли как-нибудь».
Ответы API оформляют единым форматом ошибки (task_79).

Проверка Postman-коллекцией (task_76) включает негатив: повтор того же
заказа, неизвестный товар, пустой JSON — каждый со своим ожидаемым кодом.
Сценарий «создать→повторить→проверить один документ» — первый
контрактный тест квартала.

Три проверки, которые делают на ревью неглядя: тот же заказ повторно —
один документ; товар без сопоставления — 422 и список позиций; заказ
без externalId — 400, а не «присвоили наш». Типичные ошибки: уникальность
externalId держать дисциплиной, а не контролем в транзакции; цены
заказа пересчитывать из наших ценников (магазин шлёт свою цену —
расхождение предмет сверки, а не перезаписи); статус заказа строкой
вместо перечисления (статус-машина task_124 потом не соберётся).
Ответ API на успех содержит номер нашего документа: по нему магазин
и поддержка говорят об одном заказе.

Частичный успех честнее полного отказа: заказ из 50 строк, где
3 строки битые, принимается 47 строками с явным списком отклонённых,
а не падает целиком или молча глотает битые. Ответ перечисляет
rejected с причинами по строкам — партнёр чинит свои данные,
а не гадает. Повторная отправка того же заказа с Idempotency-Key
возвращает первый результат, а не второй заказ: ключ хранится
с результатом дольше окна повторов партнёра. Граница транзакции —
один документ: заказ не проводится «наполовину внутри документа».

ЗАДАНИЕ: что сделать
1. Создайте документ «ЗаказКлиента» (реквизиты: Контрагент, Статус, ВнешнийИдентификатор;
   табличная часть: Номенклатура, Количество, Цена) — раньше его в конфигурации не было.
   Реализуйте POST /orders: приём заказа, валидация, создание документа, возврат 201.
2. Реализуйте идемпотентность: повторный POST с тем же externalId не создаёт дубль
   (возвращает 409 или существующий ресурс).
3. Реализуйте PUT /orders/{id}/status для изменения статуса и DELETE для отмены.
4. Реализуйте приём пачки заказов (POST /orders/batch) с частичным успехом:
   в ответе — статус по каждому заказу.
5. Напишите тесты и сценарий vanessa: 20 заказов, из них 3 с ошибками.

РЕЗУЛЬТАТ (Definition of Done):
- POST/PUT/DELETE работают и соответствуют OpenAPI-контракту
- Дубли заказов исключены (проверено повторной отправкой)
- Batch-приём возвращает детализацию по каждому элементу
- Сценарий «20 заказов, 3 с ошибками» проходит

ПОДСКАЗКИ МЕНТОРА:
- Идемпотентность — не «проверить, есть ли такой заказ», а атомарная проверка с блокировкой: иначе два параллельных запроса создадут два документа.
- Частичный успех в batch — правильный выбор для интеграций: один плохой заказ не должен блокировать остальные.
