ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Магазин обновился и ждёт новое поле в ответе, а второй партнёр ещё
на старой версии и обновится через квартал. Сервис один — потребителей
много и у каждого свой темп. Сегодня API получает версии, а ошибки —
единый формат, чтобы изменения не становились сюрпризом в продуктиве.

Контракты живут годами, а партнёры обновляются в разное время. Поэтому
нужны версии API и единый, предсказуемый формат ошибки: код, сообщение, детализация,
идентификатор инцидента для поддержки.

ТЕОРИЯ: что нужно знать перед выполнением
Версионирование через URL — /hs/rih/v1/...: версия видна в адресе,
старая и новая живут рядом, потребитель переезжает, когда готов.
Внутри версии изменения только совместимые: поля добавляются,
но не удаляются и не меняют смысл. Ломающее изменение — новая
версия (v2) рядом со старой, а не «в пятницу поменяли формат».

Версия контракта (info.version в OpenAPI, task_77) и версия сервиса —
разные оси: сервис чинится патчами при неизменном контракте v1
(развитие темы — task_267). Срок жизни старой версии объявляют
заранее и фиксируют в документации партнёра (task_96), а не выясняют
по факту падения чужих клиентов в понедельник.

Единый формат ошибки RIH уже описан в docs/api/error_format.md:
{code, message, details, incidentId, timestamp}. Код — из закрытого
справочника этого документа: новый код появляется сначала там,
потом в коде. HTTP-статус говорит «что делать с запросом», код —
«что именно случилось»; message не содержит стека, секретов
и персональных данных.

Порядок внедрения: сначала общий обработчик, превращающий любое
исключение маршрута в формат ошибки и пишущий тот же incidentId
в журнал регистрации; затем справочник кодов в документации;
затем тесты на классы ошибок: 400 на мусор, 401 без ключа,
404 на неизвестный ресурс, 500 — с incidentId в ответе и в журнале.

Структура ошибки рождается в одном месте: её собирает
РИХ_ОбщегоНазначения.СтруктураОшибки() (создаётся в этом задании,
правило 5 error_format.md), а модуль ответов task_74 оборачивает
структуру в HTTPСервисОтвет. Пять маршрутов, собирающих ошибку
вручную каждый по-своему, дадут пять диалектов одного формата.

Единый формат ошибки — часть контракта обеих сторон: code для
кода, message для человека, details для разбора, incidentId для
поиска в журналах (task_84). Формат не меняется внутри мажорной
версии API; новое поле добавляется, существующие не переименовываются.
Клиент обязан различать «ошибку бизнеса» (повтор не поможет)
и «ошибку доступности» (повтор по политике task_128). Ошибка без
incidentId превращает обращение в поддержку в пересказ своими
словами — это и есть главная цена несоблюдения формата.

ЗАДАНИЕ: что сделать
1. Реализуйте версионирование через URL (/api/v1/...) и проверьте, что
   v1 и v2 могут сосуществовать.
2. Спроектируйте единый формат ошибки: {code, message, details, incidentId, timestamp}.
3. Реализуйте общий обработчик ошибок сервиса: любое исключение → формат ошибки +
   запись в журнал регистрации с incidentId.
4. Составьте справочник кодов ошибок RIH (минимум 12 кодов) и положите в документацию.
5. Напишите тесты: 400 на мусор, 401 без ключа, 404 на неизвестный ресурс, 500 с incidentId.
