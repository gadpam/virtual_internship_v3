ЗАДАНИЕ task_105 · спринт 18 · Q2
Тема спринта: КД 3.0, версии обменов, распределённая база
Идемпотентность и дубли в обменах

Оценка времени: 4 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Ночной обмен применился дважды: сеть моргнула, отправитель повторил,
приёмник честно создал вторые документы. Сегодня приёмник учится
узнавать «я это уже видел» — на уровне сообщений и бизнес-объектов.

Сообщения теряются, повторяются, приходят не по порядку. Если приёмник
не идемпотентен, повторное сообщение создаст второй документ, второй приход,
вторые деньги. Идемпотентность — базовое свойство промышленного обмена.

ТЕОРИЯ: что нужно знать перед выполнением
Идемпотентность приёмника строится на журнале принятых сообщений:
messageId, источник, дата, статус обработки, результат. Проверка «было
ли» и запись «теперь есть» обязаны быть атомарны (одна транзакция /
блокировка по ключу): два параллельных потока иначе оба «не найдут»
сообщение и оба применят — гонка из task_45 в интеграционном виде.

Повтор после частичной обработки — самое тонкое место: сообщение из
100 документов применилось на 60. Журнал на уровне сообщения скажет
«было», а правда — «частично». Лечение: идемпотентность каждого
бизнес-объекта внутри (по externalId документа) плюс журнал шагов —
тогда повтор дообрабатывает хвост, а не дублирует голову.

Дубли с разными messageId (источник пересоздал сообщение) ловит
детектор по externalId: объект с таким внешним ключом уже есть —
это повтор бизнес-сущности, каким бы новым ни был конверт.

Хранить messageId надо дольше периода возможных повторов; тест из
задания (100 сообщений, 20 дублей) обязан дать ноль дублей в данных.

Тест из задания разбирают по журналу: 120 входящих, 100 применено,
20 повторов узнано по messageId, ещё сценарий «тот же заказ, новый
messageId» остановлен детектором по externalId. Типичные ошибки:
журнал сообщений без результата обработки (нечем ответить на повтор);
проверка «было ли» и запись в разных транзакциях без блокировки;
messageId хранить неделю при периоде повторов в месяц.

Проверка понимания: отправитель повторил сообщение через месяц.
Откуда приёмник знает, что это повтор, и что для этого должно было
быть спроектировано в первый день?

Идемпотентность обмена проверяется худшим тестом: тот же пакет
применяется дважды и трижды, результат сверяется по документам,
движениям и остаткам — «дублей не видно в журнале» не доказательство.
Ключ идемпотентности живёт дольше окна повторов: повтор через сутки
после очистки ключей равен первому пакету. Дубли справочников лечатся
поиском соответствий (task_213), а не удалением: удаление дубля
с движениями разрушает историю. Счётчик принятых/отклонённых/дублей —
обязательная строка протокола каждого обмена.

ЗАДАНИЕ: что сделать
1. Реализуйте хранение принятых сообщений: уникальный идентификатор сообщения,
   дата, статус обработки, результат.
2. Реализуйте отказ от повторной обработки: то же messageId → тот же результат.
3. Обработайте случай «повтор после частичной обработки»: как понять, что сделано,
   а что нет?
4. Реализуйте детектор дублей бизнес-объектов (один заказ пришёл дважды с разными
   messageId) — по externalId.
5. Проведите тест: отправьте 100 сообщений, 20 из них дубли. Проверьте результат.

РЕЗУЛЬТАТ (Definition of Done):
- Повторная обработка не создаёт дублей (проверено)
- Детектор дублей по externalId работает
- Сценарий частичной обработки описан и реализован
- Тест «100 сообщений, 20 дублей» пройден с нулём дублей в данных

ПОДСКАЗКИ МЕНТОРА:
- Идемпотентность требует атомарной проверки: блокировка по ключу сообщения в момент проверки. Иначе два параллельных потока оба «не найдут» сообщение.
- Храните messageId долго (минимум период обмена): иначе дубль через месяц пройдёт как новый.
