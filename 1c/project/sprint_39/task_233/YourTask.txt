ЗАДАНИЕ task_233 · спринт 39 · Q4
Тема спринта: Python для 1С-разработчика: минимум для совместной работы с AI-командой
Python ↔ 1С: вызовы, форматы, ошибки, таймауты

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Два мира встречаются: 1С вызывает Python-сервис, получает JSON,
а дальше — кодировки, даты, числа с плавающей точкой и 500-е.
Сегодня клиент РИХ_AIКлиент строится по всем правилам надёжности Q2.

Интеграция двух миров: 1С вызывает Python-сервис по HTTP, получает JSON,
обрабатывает ошибки. Здесь важна согласованность контрактов, кодировок, дат, чисел
и поведения при сбоях.

ТЕОРИЯ: что нужно знать перед выполнением
Общий модуль РИХ_AIКлиент — единая точка вызовов AI-сервиса из 1С:
доступность (health), основной вызов, обработка ошибок. Контрактные
соглашения фиксируются обеими сторонами: даты — ISO 8601 в UTC,
строки — UTF-8 (кириллица проверяется на реальных данных, а не на
«test»), числа с плавающей точкой — с явной точностью или строкой:
float в JSON между системами — классический источник расхождений
на копейках.

Надёжность наследуется из Q2 дословно: явные таймауты (task_127),
ретраи только на повторяемые ошибки (task_128), circuit breaker
(task_129) — модули Q2 переиспользуются, а не переписываются под
новый сервис. Четыре сценария теста: недоступен, 500, мусор вместо
JSON, корректный ответ; у каждого — своё поведение клиента и запись
в ЖурналИнтеграций.

Контракт сверяется с OpenAPI сервиса (Swagger из task_231): расхождение
полей находится сверкой, а не первым упавшим запросом.

Сценарии таблицей: сервис недоступен — понятная ошибка пользователю
и запись в ЖурналИнтеграций; 500 — ретрай по правилам, мусор — отказ
без падения формы. Типичные ошибки: таймаут не ставить («сервис же
свой»); число 0.1 + 0.2 сравнивать между системами до копейки;
circuit breaker копировать кодом вместо модулей Q2.

Проверка понимания: назовите, как ваш клиент ведёт себя в каждом из
четырёх сценариев — недоступен, 500, мусор, корректный ответ, —
и покажите запись ЖурналаИнтеграций по одному из них. Клиент,
у которого сценарии различаются только текстом исключения,
контракт надёжности Q2 не унаследовал.

Клиент 1С к AI-сервису — такой же интеграционный клиент, как
в Q2: таймауты task_127, повторы task_128, breaker task_129
переиспользуются, а не переписываются под «свой» сервис.
Числа JSON между мирами — строкой или с явной точностью: float
расходится на копейках и находится сверкой, а не тестом.
Даты ISO 8601 UTC на стыке обязательны: локальное время двух
систем разъезжается незаметно и навсегда. Кириллица проверяется
реальным текстом регламентов, а не словом test.

ЗАДАНИЕ: что сделать
1. Реализуйте в RIH общий модуль `РИХ_AIКлиент` с методами: проверить
   доступность, получить ответ сервиса, обработать ошибку.
2. Обеспечьте передачу дат в ISO 8601 UTC, чисел с явной точностью, строк в UTF-8.
3. Реализуйте таймауты, ретраи и circuit breaker (используйте модули Q2).
4. Напишите тест: сервис недоступен, сервис вернул 500, сервис вернул мусор,
   сервис вернул корректный ответ.
5. Зафиксируйте контракт в OpenAPI обеих сторон и сверьте его.
