ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Сборка конфигурации руками перед каждым демо съедала час и однажды собрали
не те исходники. Сегодня конвейер: коммит → проверки → сборка → артефакт,
одинаково у всех и без участия человека.

Команда из 250 человек не может жить без автоматизации: сборка конфигурации
из исходников, публикация на тестовый стенд, прогон тестов, отчёт о качестве, артефакты.
Всё это настраивается один раз и работает годами.

ТЕОРИЯ: что нужно знать перед выполнением
CI (continuous integration) — автоматическая проверка каждого изменения:
workflow GitHub Actions описывает шаги (jobs/steps) на YAML: взять исходники,
поставить инструменты, прогнать линт и валидацию, собрать артефакт,
опубликовать его. Наш шаблон живёт в internship/tools/ci/github-actions и
копируется в .github/workflows форка.

Сборка .cf из EDT-исходников делается EDT в headless-режиме или
vanessa-runner: исходники → валидация → сборка конфигурации → Rih.cf
артефактом прогона. Упирается в лицензии: раннерам GitHub нужна своя
платформа/EDT; без лицензий честный минимум CI — линт, валидация структуры
исходников и Python-тесты стенда, а сборка остаётся локальной с фиксацией
причины (стыковка с task_265 в Q4).

Дымовые тесты в CI (vanessa, task_53) — следующий рубеж после сборки;
branch protection запрещает слияние при красных проверках: правило
настраивается на форке и описывается в документации, чтобы новый
разработчик не «чинил» красный CI отключением проверок.

Артефакт с манифестом (версия, коммит, контрольные суммы) — то, что
отличает «собрали что-то» от релиза: любой Rih.cf можно связать
с исходниками, из которых он собран.

Минимальный честный workflow учебного форка: checkout → линт BSL →
проверка структуры EDT-исходников → артефакт документации; шаг сборки
.cf включён, когда у форка есть лицензии, и помечен условием, а не
удалён. Типичные ошибки: секреты в workflow текстом (ключи — только
secrets); кэширование «чего-нибудь», что маскирует грязную сборку;
зелёный workflow, который ничего не проверяет (пустые шаги).
Проверка конвейера: сломайте BSL-строку в отдельной ветке и убедитесь,
что CI упал именно на линте, — это и есть доказательство работы.

CI для 1С честно разделяется на то, что реально делает раннер
без лицензии платформы (валидация исходников, тесты Python,
статический анализ), и то, что требует лицензии (сборка .cf,
прогон vanessa). Смешивать это в один зелёный статус нельзя:
манифест сборки перечисляет, что именно проверено. Артефакт CI
хранится с коммитом и сроком: «собиралось когда-то» без привязки
к версии не является доказательством. Падение CI — событие
с владельцем, как падение ночных тестов (task_266).

ЗАДАНИЕ: что сделать
1. Изучите workflow в internship/tools/ci/ и опишите, что делает каждый шаг.
2. Добавьте шаг сборки .cf из исходников EDT (vanessa-runner / edt-CLI). Если
   лицензий EDT/платформы для CI у вас нет — шаг выполняет валидацию исходников,
   а сборка .cf остаётся локальной; зафиксируйте это в документации честно.
3. Добавьте шаг публикации артефакта (Rih.cf) в артефакты GitHub Actions.
4. Добавьте шаг прогона дымовых тестов с отчётом (vanessa-runner --allure или текстовый отчёт).
5. Настройте так, чтобы PR не сливался при красных проверках (branch protection описать
   в документации, настроить на своём форке).

РЕЗУЛЬТАТ (Definition of Done):
- CI собирает .cf и публикует артефакт (или, без лицензий в CI, — валидирует исходники, а .cf собирается локально)
- Дымовые тесты запускаются в CI, отчёт виден
- Описаны шаги workflow в документации
- Правило branch protection описано (или настроено на форке)

ПОДСКАЗКИ МЕНТОРА:
- Сборка конфигурации в CI требует лицензии/платформы на раннере. Для учебного стенда можно собирать только валидацию и тесты на mock-данных — это тоже ценность.
- Не храните секреты в коде: используйте GitHub Secrets.
