ЗАДАНИЕ task_183 · спринт 31 · Q3
Тема спринта: MS SQL Server глазами разработчика 1С
Обработка данных скриптами: безопасно и воспроизводимо

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Нужно поправить данные в базе скриптом: дубли справочника слить,
реквизит заполнить, ссылки перенести. Один UPDATE без WHERE — и это
уже не задача, а инцидент. Сегодня скрипты обработки данных получают
правила безопасности.

Рано или поздно нужно поправить данные скриптом: очистить дубли, заполнить
реквизит, перенести значения. Делать это надо так, чтобы скрипт можно было проверить,
повторить и откатить — иначе одна опечатка станет инцидентом.

ТЕОРИЯ: что нужно знать перед выполнением
Анатомия безопасного скрипта: проверка предусловий (SELECT с тем же
WHERE и человеческая сверка количества строк) → архив «до»-состояния
затронутых строк → транзакция → изменение → подсчёт затронутых
и сравнение с ожиданием → фиксация или откат → запись в журнал
выполнения (кто, когда, скрипт, сколько строк). Dry run — тот же
скрипт с режимом «только показать»: сначала смотрят план изменений,
потом разрешают боевое выполнение.

Откат проектируется до запуска: архивная таблица позволяет вернуть
строки точечно; «у нас есть бэкап» — не откат, а катастрофа с
восстановлением всей базы и потерей чужих изменений за день.

Регламент продуктива: согласование, окно обслуживания, исполнитель
и проверяющий, проверка результата после. Правка данных SQL-ом в обход
1С — исключение с разрешением администратора (целостность платформы —
task_181), а не повседневный инструмент.

Тестовая копия базы — место первой пробежки скрипта, всегда.

Проверка dry run: скрипт показал «будет обновлено 1 240 строк»,
бухгалтер подтвердил цифру до боевого прогона, архив «до» лёг
рядом. Типичные ошибки: SELECT для проверки и UPDATE писать разными
условиями; архив делать после изменения («уже нечего архивировать»);
скрипт не версионировать — через месяц его правят с продакшн-копии.

Проверка понимания: скрипт обновил 12 400 строк вместо ожидаемых
1 240. Что должно произойти в следующие 60 секунд по анатомии
безопасного скрипта — и что, если архива «до» не оказалось?

Скрипт обработки данных — это мини-релиз: dry run показывает,
что будет изменено; транзакция ограничивает цену ошибки;
архив «до» позволяет откат; журнал скрипта отвечает «что
сделано» цифрами. Скрипт без dry run на продуктиве не запускается
никогда — это правило ревью task_223. Повторный запуск скрипта
идемпотентен (task_105): скрипт, который «только один раз»,
при втором запуске становится инцидентом. Объёмные скрипты
идут пакетами task_57: час в одной транзакции — час блокировок.

ЗАДАНИЕ: что сделать
1. Реализуйте учебную задачу очистки: устранить дубли справочника и перенести
   ссылки на основной элемент (в тестовой копии базы).
2. Напишите скрипт по правилам: проверка предусловий, транзакция, подсчёт затронутых
   строк, логирование в таблицу-журнал, откат при ошибке.
3. Добавьте «dry run» режим: скрипт показывает, что изменит, но не меняет.
4. Реализуйте сохранение «до»-состояния затронутых строк (таблица-архив) для отката.
5. Составьте регламент выполнения скриптов на продуктиве: кто согласовывает, где
   запускает, как проверяет результат.

РЕЗУЛЬТАТ (Definition of Done):
- Скрипт работает в dry run и в боевом режиме
- Есть транзакция, подсчёт строк и журнал выполнения
- Архив «до»-состояния позволяет откат
- Регламент выполнения скриптов сохранён

ПОДСКАЗКИ МЕНТОРА:
- UPDATE без WHERE — классическая катастрофа. Всегда сначала SELECT с тем же WHERE и проверка количества строк.
- Правки данных в обход 1С ломают целостность платформы (кэши, индексы, версионирование). Согласуйте такие операции с администратором и делайте их в окно обслуживания.
