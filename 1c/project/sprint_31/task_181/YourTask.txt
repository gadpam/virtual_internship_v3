ЗАДАНИЕ task_181 · спринт 31 · Q3
Тема спринта: MS SQL Server глазами разработчика 1С
Как 1С хранит данные в СУБД: таблицы, поля, ссылки

Оценка времени: 2 ч
Уровень задания: расширение — углубление темы; при отставании переносится на следующую неделю

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
СУБД для разработчика 1С обычно — чёрный ящик: «там таблицы какие-то».
Сегодня смотрим, как объекты метаданных ложатся в таблицы MS SQL:
справочник, документ с табличной частью, регистр — своими глазами в SSMS.

Между объектом метаданных и таблицей СУБД есть отображение: справочник —
это _ReferenceNN, документ — _DocumentNN, регистр — _AccumRgNN/_InfoRgNN, поля
имеют префиксы и типы (ссылки хранятся как составные ключи). Понимание этого
превращает СУБД из чёрного ящика в рабочий инструмент. Базовые SELECT, JOIN и
GROUP BY вы выполняли в task_11; здесь разбираем, как 1С раскладывает объекты
метаданных по таблицам СУБД.

ТЕОРИЯ: что нужно знать перед выполнением
Отображение метаданных в СУБД: справочник — таблица _Reference<id>,
документ — _Document<id> плюс отдельные таблицы табличных частей,
регистры накопления — _AccumRg<id>, сведений — _InfoRg<id>. Идентификаторы
берутся из конфигурации/системных таблиц, а не угадываются.

Поля: ссылка объекта — составной ключ с типом; реквизиты — колонки
с префиксами; табличная часть хранится отдельными строками со ссылкой
на владельца и номером строки. Виртуальные таблицы 1С (остатки, обороты,
срез) в СУБД отсутствуют: они вычисляются запросами платформы поверх
«сырых» таблиц и итогов — поэтому строить отчётность по сырым таблицам
значит переизобрести итоги с ошибками.

Читать сырые таблицы полезно для диагностики («что реально записано»),
писать в обход платформы запрещено: кэши, регистрация изменений,
индексы и версионирование останутся в неведении, база станет
несогласованной. Конспект соответствия «объект → таблица → поля» —
рабочий инструмент на все спринты SQL.

База — серверная ИБ RIH на MS SQL (task_150); при PostgreSQL-контуре
имена таблиц те же, инструменты — pgAdmin/psql.

Чтение таблицы документа: шапка в _Document<id>, строки ТЧ — в её
таблице табличной части со ссылкой на владельца; сравнение с запросом 1С
показывает, что виртуальная таблица остатков посчитала итоги, которых
в сырых движениях «готовой цифрой» нет. Типичные ошибки: угадывать
номера таблиц по порядку создания; строить отчёт по сырым таблицам
вместо витрины; писать в таблицы SQL-ом «быстро поправить».

Проверка понимания: коллега предлагает «быстренько поправить
остатки UPDATE-ом». Назовите три последствия для платформы из
теории одной фразой каждое.

Имена таблиц СУБД не обещаются платформой навсегда: прямой SQL
по физическим таблицам — долг, который платится при обновлении
платформы (task_287 для СУБД). Ссылки в СУБД — это идентификаторы,
а не «красивые ключи»: соединение по ссылке делается через
преобразование, известное платформе. Понимание физического
хранения нужно для планов (task_187) и объёмов (task_185),
а не для обхода платформенных запросов «потому что быстрее»:
быстрее ровно до первого расхождения итогов.

ЗАДАНИЕ: что сделать
1. Подключитесь к серверной ИБ RIH на MS SQL (подготовлена в task_150) через
   SSMS/ADS и найдите таблицы, соответствующие справочнику Номенклатура,
   документу ПоступлениеТоваров, регистру ТоварыНаСкладах. Если вместо MS
   SQL у вас PostgreSQL, спринты 31–32 выполняются на нём аналогами
   (pgAdmin/psql, pg_stat_activity), а расхождения фиксируются в конспекте.
2. Разберите структуру: ключевые поля, поля реквизитов, табличные части (строки),
   поля-ссылки и их типы.
3. Выполните 5 T-SQL-запросов: выбрать товары, строки документа, движения регистра,
   соединить документ со справочником, посчитать суммы.
4. Сравните результат с запросом 1С и объясните различия (виртуальные таблицы vs сырые данные).
5. Сохраните конспект соответствия «объект метаданных → таблица СУБД» в документации.

РЕЗУЛЬТАТ (Definition of Done):
- Найдены и описаны минимум 6 таблиц с назначением полей
- 5 T-SQL-запросов выполнены, результаты сверены с 1С
- Конспект соответствия сохранён
- Объяснено, почему нельзя строить отчёты прямо по сырым таблицам

ПОДСКАЗКИ МЕНТОРА:
- Сырые таблицы не содержат виртуальных расчётов (остатки, обороты): их надо считать самому, и легко ошибиться. Для аналитики используйте витрины.
- Имена таблиц содержат числовые идентификаторы объектов — берите их из конфигурации/технологических таблиц, а не угадывайте.
