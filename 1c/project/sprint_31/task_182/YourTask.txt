ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Вопрос аналитика: «топ товаров с долей, нарастающим итогом и динамикой
к прошлому месяцу одним запросом». В 1С это был бы подвиг, в T-SQL —
оконные функции и CTE. Сегодня аналитический SQL становится рабочим
инструментом расследований.

Анализ данных в СУБД часто быстрее и гибче, чем в 1С: оконные функции,
CTE, GROUPING SETS. Эти инструменты нужны для расследований («почему цифры не
сходятся») и для подготовки данных перед массовой обработкой.

ТЕОРИЯ: что нужно знать перед выполнением
CTE (WITH …) разбивает запрос на именованные шаги: читабельность
и повторное использование результата внутри запроса; сравнение
с вложенными подзапросами — по времени на ваших данных, а не по вкусу.
Оконные функции считают по «окну» строк без свёртки: доля (SUM OVER),
ранг (ROW_NUMBER/RANK), динамика (LAG/LEAD), накопительный итог
(SUM OVER ORDER BY). GROUPING SETS даёт итоги нескольких уровней
группировки одним проходом.

Два прикладных запроса из задания ценнее шести учебных: дубли по
бизнес-ключу (GROUP BY … HAVING COUNT > 1) и «осиротевшие» записи
(строки ТЧ без документа, движения без регистратора — LEFT JOIN …
WHERE ключ IS NULL). Они находят грязь данных, которую интерфейс
не покажет никогда.

Дисциплина больших таблиц: во время разработки запросы ограничивают
(TOP, отборы по периоду), иначе каждый эксперимент стоит минуты
и чужие блокировки. Скрипты живут в tools/sql/analysis с комментариями:
запрос без комментария через месяц не читается даже автором.

Пример одной строкой: доля товара в продажах дня — SUM(Сумма) OVER
(PARTITION BY День) рядом с суммой строки, без самосоединения.
Типичные ошибки: окно без PARTITION считать «по всем данным» молча;
дубли искать по наименованию вместо бизнес-ключа целиком; запрос
находить «осиротевших» гонять по всей базе без ограничения периода
в рабочее время.

Проверка понимания: запрос «сирот» нашёл движения без регистратора.
Это точно ошибка данных? Назовите легальную ситуацию, где
регистратор может отсутствовать, прежде чем чистить.
