ЗАДАНИЕ task_127 · спринт 22 · Q2
Тема спринта: Надёжность интеграций: ретраи, таймауты, компенсации, деградация
Таймауты: как одно значение спасает (или топит) систему

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Один партнёрский API «задумался» на 40 секунд — и вместе с ним встали
десятки сеансов 1С, каждый со своим ожиданием. Разбор показал: таймаутов
не стояло вообще. Сегодня таймауты становятся явными и измеренными.

Значение таймаута по умолчанию — это лотерея. Слишком большой — зависшие
сеансы и исчерпанные соединения; слишком маленький — ложные ошибки при нагрузке.
Таймауты должны быть явными, разными для разных операций и измеренными.

ТЕОРИЯ: что нужно знать перед выполнением
Таймаут — граница ожидания внешнего вызова. Различают connect
(установить соединение), read (ждать ответ) и общий бюджет операции;
у HTTPСоединения 1С задаётся общий таймаут соединения. Вызов без
таймаута занимает поток, сеанс и — хуже всего — блокировки, если
случился внутри транзакции (запрет из task_44).

Значение не берут «с потолка»: измеряют p95 длительности успешных
вызовов под нагрузкой и ставят таймаут с запасом над ним. Слишком
маленький таймаут рождает ложные ошибки (партнёр успел, мы уже
отвалились), слишком большой возвращает проблему из легенды.

Главное следствие таймаута — неопределённость: «не знаю, выполнилось
ли». Поэтому у операции бывает проверка состояния у партнёра
(запрос статуса по нашему идентификатору) и идемпотентность повтора:
повторить после таймаута можно только операцию, которая от повтора
не задвоится (task_105). Платежи после таймаута не повторяют слепо.

Инвентаризация всех внешних вызовов с таблицей таймаутов закрывает
класс «а здесь забыли» системно, а не по инцидентам.

Пример строки таблицы: «ТК, расчёт доставки: p95 1.8 с, таймаут 5 с,
при таймауте — заявка без расчёта + очередь повторной проверки».
Типичные ошибки: один таймаут «30 секунд на всё» по наследству;
таймаут ставить без замера p95 под нагрузкой (на пустом стенде все
вызовы быстрые); после таймаута повторять платёж, не спросив статус
у партнёра (путь к двойному списанию из task_118).

Проверка понимания: вызов упал по таймауту, а операция у партнёра
выполнилась. Каким запросом вы это узнаете и почему «просто
повторить» здесь может стоить денег?

Таймаут — это обещание «дольше не ждём», и оно задаётся на
каждом участке цепочки: клиент ждёт меньше, чем сервер обрабатывает,
прокси — дольше сервера (task_260). Таймаут по умолчанию равен
его отсутствию: вызов висит вместе с формой и рабочим процессом.
Сумма таймаутов цепочки считается: пользовательский сценарий
не может обещать 5 секунд при трёх вызовах по 4. Каскадные
таймауты проверяются остановкой самого медленного звена:
именно там рождаются «всё зависло из-за одного партнёра».

ЗАДАНИЕ: что сделать
1. Проведите инвентаризацию всех внешних вызовов RIH и выпишите текущие таймауты.
2. Установите явные таймауты: connect, read, общий — по типам операций.
3. Экспериментально подберите значения: замерьте p95 длительности успешных вызовов
   на стенде под нагрузкой.
4. Реализуйте поведение при таймауте: что делаем с операцией, которая «возможно
   выполнилась» на стороне партнёра?

ПОДСКАЗКИ МЕНТОРА:
- Таймаут — это «не знаю, что произошло», а не «не произошло». Это ключевое различие, которое забывают: нужна проверка состояния у партнёра.
- Особый случай — вызов внутри транзакции: там таймаут держит блокировки. См. task_44.
