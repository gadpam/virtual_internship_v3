ЗАДАНИЕ task_301 · спринт 51 · Q4
Тема спринта: Финальная сборка: единая система и сквозной сценарий
Интеграционная сборка: все контуры в одном стенде

Оценка времени: 6 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Все контуры года жили по отдельности и ни разу не собирались вместе.
Сегодня полный стенд поднимается одной командой: 1С, СУБД, партнёры,
очередь, AI, BI и мобильность — с зелёными healthcheck у всех.

Весь год вы строили контуры по отдельности. Финальная задача — собрать
их в один стенд и убедиться, что всё работает вместе: 1С + СУБД + mock-партнёры +
очередь + AI-сервис + BI + мобильное приложение.

ТЕОРИЯ: что нужно знать перед выполнением
Интеграционная сборка использует полный контур стенда
(docker-compose.full.yml плюс профили task_262): порядок подъёма —
данные и СУБД, платформа, сервисы, BI; healthcheck каждого
сервиса зелёный до следующего этажа, иначе отладка превращается
в хаос из семи неизвестных.

Эталонные данные наполняют все контуры согласованно: товары,
склады, заказы, чеки, проводки, витрины, корпус знаний —
одна «правда» на стенд, иначе сквозные проверки task_302
будут сравнивать разные миры.

Связность проверяется путями, а не сервисами по одному: мобильное
приложение → витрина → дашборд; ошибка интеграции → журнал →
объяснение ассистента.

Время сборки и ресурсы фиксируются: финальный стенд обязан
воспроизводиться через полгода по версиям компонентов.

Сборка по этажам: СУБД и очередь — 3 минуты, сервисы — 5, BI — 4;
связность доказана мобильной операцией, видимой в дашборде.
Типичные ошибки: поднимать всё сразу и отлаживать семь сервисов
одновременно; эталонные данные делать разными для контуров;
версии компонентов не фиксировать в сборке года.

Проверка понимания: покажите мобильную операцию, видимую в дашборде,
пройдя её путь через все контуры по журналам. Путь, который
нельзя пройти по следам систем, собран стендом из островов,
а не интеграционной сборкой.

Порядок подъёма документируется зависимостями, а не списком
команд: коллега понимает, почему BI ждёт витрины. Ресурсы
стенда (RAM/CPU/диск) фиксируются: «тяжёлый стенд» без цифр
нельзя спланировать на машине новичка. Финальный стенд имеет
тег версий всех компонентов: через полгода он поднимается
тем же, а не «последним, что тогда работало».

ЗАДАНИЕ: что сделать
1. Обновите docker-compose: все сервисы года в одном файле с профилями.
2. Поднимите полный стенд одной командой и проверьте healthcheck каждого сервиса.
3. Наполните эталонными данными: товары, склады, заказы, чеки, проводки, витрины,
   корпус знаний.
4. Проверьте связность: данные из мобильного приложения доходят до витрины и дашборда;
   ошибка интеграции видна в журнале и объясняется AI-ассистентом.
5. Зафиксируйте время полной сборки стенда и объём ресурсов.

РЕЗУЛЬТАТ (Definition of Done):
- Полный стенд поднимается одной командой (7+ сервисов)
- Healthcheck всех сервисов зелёный
- Эталонные данные загружены, связность проверена
- Время сборки и ресурсы зафиксированы

ПОДСКАЗКИ МЕНТОРА:
- Собирайте стенд постепенно: сначала данные и СУБД, потом 1С, потом сервисы, потом BI. Иначе отладка превратится в хаос.
- Фиксируйте версии всех компонентов: финальный стенд должен быть воспроизводим через полгода.
