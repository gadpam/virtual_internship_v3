ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Магазин прислал заказ «в теле письма», а модуль HTTP-ответов висит уже в стартовой
конфигурации не просто так: сегодня наши первые настоящие HTTP-запросы —
руками, с заголовками и кодами ответов, а не «как-нибудь отправилось».

REST — это не «JSON по HTTP». Это соглашение: ресурсы, методы, коды
состояний, идемпотентность. Ошибка новичка — возвращать 200 на всё подряд и класть
текст ошибки в тело ответа. Контракт-партнёр по такому API работать не сможет.

ТЕОРИЯ: что нужно знать перед выполнением
HTTP — протокол запрос/ответ. Запрос: метод (GET — получить, POST — создать/
действие, PUT/PATCH — обновить, DELETE), URL, заголовки, тело. Ответ: код
состояния, заголовки, тело. Коды — контракт, а не украшение: 2xx успех (200,
201 создан), 4xx ошибся клиент (400 неверные данные, 401 нет авторизации,
404 нет ресурса, 409 конфликт состояния), 5xx ошиблась система. Клиент
обязан ветвиться по коду, а не парсить тело в надежде на удачу.

Заголовки несут смысл: Content-Type говорит, что в теле (application/json),
Authorization — кто ты (Bearer token, Basic), Accept — что готов принять.
Тело JSON — текст: кодировка UTF-8 по умолчанию; не-ASCII в 1С требует
внимания при ручной сборке строк (методы модуля РИХ_HTTP1_Ответы — ваш
стартовый набор подсистемы, и дополнение из задания — ваши первые правки
в нём).

Код статуса проверяют до разбора тела: 500 с HTML-страницей ошибки парсерить
как JSON — классический способ спрятать настоящую ошибку под «невалидный JSON».
Подробные правила статуса и повторных запросов разложит task_129.

Первый запрос из Postman, а не из кода: увидеть «сырой» обмен глазами —
заголовки, время, тело; потом тот же запрос повторяют кодом 1С и сверяют
ответы. Разница между «у Postman работает» и «из 1С работает» — обычно
авторизация, кодировка или прокси, и журнал фиксирует, какие именно.

Специфика 1С как клиента: HTTPСоединение и HTTPЗапрос платформенные;
таймаут задавайте всегда (виснувший вызов = виснувший пользователь);
сертификаты HTTPS на стенде — ещё один источник «у Postman работает,
из 1С нет». Типичные ошибки: не проверять КодСостояния и парсить тело
ошибки как данные; складывать JSON руками конкатенацией (кавычки в
наименовании товара сломают всё — есть ЗаписьJSON); секрет в URL
(попадёт в логи прокси и журнала). Итоговый модуль отвечает трем
возможностям: ответ, HTTP-ошибка, транспортная ошибка — трём разным
веткам у вызывающего, а не одной «не получилось».

Идемпотентность различается по методам: GET и PUT обязаны быть
безопасны к повтору архитектурно, POST — только с ключом
идемпотентности, который придёт в task_83. Статусы отвечают
классами: 4xx — чини запрос, 5xx — можно повторять по политике,
429 — уважай Retry-After (task_93). Тело ошибки так же контрактно,
как тело успеха: клиент парсит его кодом, а не человеком
(task_82). Время и даты в API — всегда с часовым поясом,
иначе стыки систем разъезжаются на часы молча.
