ЗАДАНИЕ task_139 · спринт 24 · Q2
Тема спринта: Тестирование интеграций: стенды, данные, контрактные и e2e-тесты
Тестовые стенды и воспроизводимые данные

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Интеграционные тесты падают «как-то по-разному»: у одного разработчика
зелёные, у второго — база пустая, у третьего mock старый. Сегодня стенды
получают описания, а тестовые данные — детерминированность.

Интеграционные тесты бессмысленны, если данные каждый раз разные. Нужны
стенды, которые поднимаются одной командой, и эталонные наборы данных, которые
загружаются детерминированно.

ТЕОРИЯ: что нужно знать перед выполнением
Три стенда — три назначения: dev (разработчик, данные любые), test
(автоматические тесты, данные детерминированные), integration (mock-
сервисы партнёров, контрактные сценарии). Описание стенда: состав
сервисов, как поднимается, где секреты (не значения — где брать).

Эталонные данные загружаются скриптом/обработкой: 500 товаров,
20 складов, 100 заказов, прайс, остатки. Детерминированность —
фиксированные идентификаторы, даты и суммы: два прогона дают
байт-в-байт одинаковую базу. Случайный генератор в тестах — источник
«плавающих» падений, после которых тестам перестают верить.

Одна команда «поднять стенд и прогнать тесты» (compose test-стенда
уже есть — docker-compose.test.yml) убирает «у меня работает»:
окружение собирается из репозитория, а не из памяти машины.

Фикстуры живут в репозитории (tests/fixtures, наследие task_96):
прогон одинаков у всех участников потока. Время подъёма и прогона
фиксируется — стенд, который поднимается час, не запускают.

Приёмка детерминированности: два поднятия стенда, контрольные суммы
фикстур совпали, прогон тестов дал одинаковый результат. Типичные
ошибки: даты в фикстурах «сегодня» (завтра тесты считают другой период);
идентификаторы случайные при фиксированных суммах — тесты ищут объекты
по id и падают; стенд поднимается «почти одной командой, только сначала
вручную вот это» — ручной шаг и есть место, где стенды расходятся.

Проверка понимания: коллега говорит «у меня тесты зелёные, у тебя
красные, код один». Назовите три различия окружения, которые ваш
стенд обязан был убрать, и где это зафиксировано.

Воспроизводимые данные — это генератор с зерном (seed), а не
копия продакшена: копия тащит ПДн, объём и невоспроизводимые
состояния. Генератор обязан уметь три объёма: малый для тестов,
средний для отладки, большой для нагрузки (task_63/143) — одним
параметром, а не тремя скриптами. Данные стенда версионируются
вместе с конфигурацией: стенд «как вчера» поднимается одной
командой (task_262). Время генерации измеряется: генератор
на 4 часа делает стенд недоступным де-факто.

ЗАДАНИЕ: что сделать
1. Опишите три стенда: dev (ваш), test (автоматические тесты), integration
   (с mock-сервисами). Для каждого — состав сервисов и способ поднятия.
2. Реализуйте скрипт/обработку наполнения эталонными данными: 500 товаров, 20 складов,
   100 заказов, прайс, остатки.
3. Обеспечьте детерминированность: одинаковые идентификаторы, даты, суммы при каждом прогоне.
4. Реализуйте команду «поднять стенд с нуля и прогнать тесты» одной строкой.
5. Замерьте время поднятия стенда и прогона.

РЕЗУЛЬТАТ (Definition of Done):
- Три стенда описаны, два из них поднимаются автоматически
- Эталонные данные детерминированы (проверено двумя прогонами)
- Одна команда поднимает стенд и запускает тесты
- Время поднятия и прогона зафиксировано

ПОДСКАЗКИ МЕНТОРА:
- Детерминированность важнее реалистичности. Генератор случайных данных в тестах — источник «плавающих» падений.
- Держите фикстуры в репозитории (internship/tests/fixtures/): тогда прогон одинаков у всех участников потока.
