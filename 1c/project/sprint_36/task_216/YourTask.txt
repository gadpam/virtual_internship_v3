ЗАДАНИЕ task_216 · спринт 36 · Q3
Тема спринта: ETL и качество данных: очистка, дедупликация, мастер-данные
Предложение по развитию данных: RFC от разработчика

Оценка времени: 2 ч
Уровень задания: резерв — буфер квартала; при отставании не выполняется

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
После квартала данных у вас есть предложение, от которого системе
станет лучше: метрики, витрина, чистка НСИ. Предложить «давайте
сделаем как я сказал» не работает. Сегодня предложение оформляется
как RFC и проходит команду.

Вакансии прямо пишут: «способность слушать, анализировать и формулировать
предложения по развитию». RFC (request for comments) — формат, в котором инженер
предлагает изменение системы и получает обратную связь до реализации.

ТЕОРИЯ: что нужно знать перед выполнением
RFC (request for comments) — инженерное предложение до реализации:
проблема с фактами и цифрами («отчёт 4 минуты, 80 запусков в день,
26 часов ожидания в месяц»), варианты (2–3, включая «ничего не делать»
с его ценой), рекомендация с критериями, оценка трудозатрат, риски,
план внедрения и метрики успеха, по которым через квартал проверят,
получилось ли.

Комментарии собираются письменно и обрабатываются по пунктам:
принято, отклонено с аргументом, изменено. Защита варианта «любой
ценой» — анти-паттерн: цель RFC — лучшее решение, иногда это
вариант комментатора. Решение фиксируется (принято/отклонено/
доработать) с именем и датой.

Принятый RFC превращается в задачи первого шага объёмом не более
спринта: большой план без первого шага останется документом.
Трудозатраты оцениваются с учётом уроков ретроспектив (оценки Q2
 расходились вдвое — task_149).

Пример зачина RFC: «Отчёт директора блокирует склад в 9:00 на
11 минут (task_190): 22 рабочих дня × 40 человек склада. Варианты:
оптимизация запроса — 3 дня; предрасчёт витрины — 2 недели;
перенос запуска — 0 дней, но данные вчерашние». Типичные ошибки:
вариант писать один, свой; оценки давать без учёта уроков ретро;
комментарии отвечать «учту» без следов в тексте.

Проверка понимания: назовите вариант «ничего не делать» из вашего RFC
и его цену в цифрах за год. RFC без этого варианта не сравнивает
решение с реальностью, а продаёт единственную идею; рецензент
обязан вернуть такой документ без рассмотрения по существу.

RFC пишется до реализации и против себя самого: автор обязан
привести сильнейший контраргумент своему варианту. Трудозатраты
оцениваются с учётом прошлой точности команды (ретро task_149:
оценки плыли вдвое) — поправочный коэффициент называется числом.
Комментарии закрываются по пунктам: принято, отклонено с причиной,
изменило текст; комментарий без следа в решении считается
незакрытым, даже если «обсудили в коридоре». Первый шаг принятого
RFC влезает в спринт: план без первого шага не начинается.

ЗАДАНИЕ: что сделать
1. Выберите проблему из области данных, которую вы видели в Q3: качество НСИ,
   производительность отчётов, дубли в обменах, отсутствие словаря метрик.
2. Напишите RFC по шаблону: проблема → данные/факты → варианты решения (2–3) →
   рекомендация → оценка трудозатрат → риски → план внедрения → метрики успеха.
   RFC сохраните в internship/documentation/rfc/ (создайте каталог).
3. Опубликуйте RFC команде/ментору и соберите комментарии.
4. Внесите правки и получите решение (принято/отклонено/доработать).
5. Если принято — заведите задачи и оцените первый шаг (не более одного спринта).

РЕЗУЛЬТАТ (Definition of Done):
- RFC написан по шаблону и содержит цифры, а не мнения
- Минимум 2 варианта решения рассмотрены с критериями
- Комментарии собраны и обработаны
- Решение зафиксировано, задачи заведены

ПОДСКАЗКИ МЕНТОРА:
- Хороший RFC начинается с фактов: «отчёт формируется 4 минуты, запускается 80 раз в день» сильнее, чем «отчёт тормозит».
- Не защищайте свой вариант любой ценой. Цель RFC — лучшее решение, а не ваша победа.
