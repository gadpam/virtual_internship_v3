Бизнес-процессы и задачи: карта маршрута и экземпляры

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Журнал интеграций показывает упавший обмен, а дальше — переписка в чате,
кто чинит. Сегодня у ошибки появляется процесс: диагностика, исправление,
проверка, закрытие — с задачами, сроками и ветвлением по критичности.

Механизм платформы: карта маршрута описывает процесс, бизнес-процесс —
экземпляр выполнения, задачи — работа конкретных исполнителей. Важно понять жизненный
цикл и то, как процесс связан с данными (например, с заявкой).

ТЕОРИЯ: что нужно знать перед выполнением
Платформенный механизм: карта маршрута описывает процесс типом
(этапы, ветвления, точки задач), бизнес-процесс — экземпляр выполнения,
задача — работа конкретного исполнителя/роли со сроком и результатом.
Жизненный цикл экземпляра: старт → задачи по этапам → завершения
этапов → завершение процесса; состояния задач и процесса — данные,
по которым потом строится аналитика (task_173).

Связь задачи с объектом — ключ удобства: задача «разобрать обмен»
содержит ссылку на сообщение обмена/заказ, исполнитель открывает
контекст в один клик, а не ищет «что-то упало вчера». Процесс,
запущенный кнопкой из журнала интеграций, стартует сразу с контекстом.

Ветвление по критичности: критичная ошибка — короткий маршрут
с эскалацией, обычная — стандартный разбор. Карту держат простой:
три простых процесса лучше одного «на все случаи», который никто
не может прочитать.

Запуск из журнала, назначение по ролям и 5 экземпляров по разным
веткам — приёмка механики.

Проверка ветвления: критичная ошибка обмена идёт маршрутом
«диагностика 30 мин → эскалация», обычная — полным циклом.
Типичные ошибки: задачи назначать конкретным людям вместо ролей
(отпуск останавливает процесс); в задачу не класть ссылку на
сообщение — исполнитель начинает с розыска контекста; завершение
задачи не двигает процесс, потому что условие перехода забыли.

Проверка понимания: задача выполнена, а процесс стоит. По каким
данным вы найдёте, на каком переходе экземпляра это произошло,
не открывая конфигуратор?

Карта маршрута — это граф состояний и переходов, а экземпляр —
конкретный документ в конкретном состоянии с историей. Логика
живёт в переходах (условия, действия), а не в формах: форма,
знающая маршрут, ломается при его изменении. Экземпляры
не удаляются: завершённый процесс — аудит, а не мусор.
Длинный процесс переживает обновления конфигурации: экземпляр,
застрявший из-за смены маршрута, разбирается как миграция данных
task_269, а не «закроем руками».

ЗАДАНИЕ: что сделать
1. Создайте карту маршрута «Разбор ошибки интеграции»: диагностика → исправление →
   проверка → закрытие, с ветвлением по критичности.
2. Реализуйте запуск процесса из журнала интеграций (кнопка «В работу»).
3. Настройте задачи исполнителям: роль, срок, приоритет.
4. Реализуйте связь задачи с объектом (сообщение обмена) и переход по ссылке.
5. Прогоните 5 экземпляров процесса с разными ветками и проверьте состояния.

РЕЗУЛЬТАТ (Definition of Done):
- Карта маршрута работает, ветвление корректно
- Запуск из журнала интеграций реализован
- Задачи назначаются по ролям и видны исполнителю
- 5 экземпляров прошли до завершения

ПОДСКАЗКИ МЕНТОРА:
- Связь задачи с данными — ключ к удобству: исполнитель должен видеть контекст без поиска по базе.
- Не делайте карту маршрута «на все случаи»: лучше три простых процесса, чем один сложный.
