Тема спринта: Безопасность интеграций: токены, секреты, ПДн, аудит
Безопасная разработка: чек-лист и ревью безопасности

Оценка времени: 2 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Перед финалом квартала безопасности ментор просит короткое: «Покажи,
по какому списку ты проверяешь новую интеграцию». Сегодня список
появляется: чек-лист безопасности и модели угроз для трёх интеграций.

Безопасность дешевле на этапе кода, чем на этапе инцидента. Нужен короткий
чек-лист, который проходит каждый PR с интеграциями, и привычка обсуждать угрозы
на этапе проектирования.

ТЕОРИЯ: что нужно знать перед выполнением
Чек-лист безопасности интеграций собирает квартал в 15+ проверяемых
пунктов: аутентификация и отзыв ключей (task_133), секреты вне кода
(134), ПДн замаскированы в логах (135), лимиты и валидация (136),
аудит действий (137), идемпотентность, таймауты, обработка ошибок
без раскрытия внутренностей. Пункт чек-листа проверяем: «да/нет/неприменимо»,
а не «вроде сделано».

Threat model одной интеграции — страница: активы (что защищаем),
акторы (кто может навредить: внешний атакующий, партнёр по ошибке,
свой сотрудник), угрозы по активам, существующие меры, остаточный
риск. Остаточный риск принимается письменно названным человеком:
«не сделано» без подписи — забывчивость, а не решение.

Ревью безопасности своих интеграций Q2 проводится по собственному
чек-листу и даёт замечания с приоритетами: закрытое в этом задании
дешевле закрытого на инциденте ровно на цену инцидента.

Чек-лист живёт в документации проекта и проходит каждый PR с
интеграциями (стыковка с ревью task_67 и Definition of Done).

Пример остаточного риска, принятого письменно: «Пентест внешнего
контура не проводим в этом квартале: сервис внутри VPN, риск принят
руководителем направления, пересмотр — к выводу наружу». Типичные
ошибки: чек-лист из общих слов без «как проверить»; threat model
писать один раз на всё и не обновлять при новой интеграции; замечания
ревью заводить без приоритетов — закрываться будут самые лёгкие.

Проверка понимания: новая интеграция пришла на ревью без threat model.
По чек-листу — какие три пункта вы проверите первыми и какое
замечание напишете, если секреты лежат в константах конфигурации?

ЗАДАНИЕ: что сделать
1. Составьте чек-лист безопасности интеграций (минимум 15 пунктов) на основе
   опыта task_133–137.
2. Добавьте его в документацию проекта: internship/documentation/security/checklist.md.
3. Проведите ревью безопасности всех своих интеграций Q2 по чек-листу.
4. Закройте найденные замечания или заведите задачи с приоритетами.
5. Оформите модель угроз (threat model) для трёх ключевых интеграций: активы, угрозы,
   меры, остаточный риск.

РЕЗУЛЬТАТ (Definition of Done):
- Чек-лист из 15+ пунктов составлен и применён
- Ревью безопасности проведено, замечания закрыты/заведены
- Threat model оформлена для 3 интеграций
- Остаточные риски приняты письменно (кто принял, почему)

ПОДСКАЗКИ МЕНТОРА:
- Threat model не должна быть толстой: активы → кто может навредить → как → что делаем → что осталось. Одна страница на интеграцию.
- Остаточный риск надо принять явно. «Мы не сделали» без подписи — это не решение, а забывчивость.
