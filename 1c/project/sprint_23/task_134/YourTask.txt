ЗАДАНИЕ task_134 · спринт 23 · Q2
Тема спринта: Безопасность интеграций: токены, секреты, ПДн, аудит
Управление секретами: где хранить пароли и ключи

Оценка времени: 3 ч
Уровень задания: ядро — обязательное; без него спринт не закрыт

ЛЕГЕНДА И КОНТЕКСТ: ситуация и зачем это нужно
Аудит нашёл пароль от СУБД в коде, ключ API в константе и .env,
закоммиченный «временно» полгода назад. Сегодня секреты получают
правильные места хранения, а репозиторий — стражу на входе.

Пароли в коде, ключи в константах конфигурации, .env в Git — три способа
получить инцидент безопасности. Секреты должны жить вне кода: в переменных окружения,
в защищённых настройках, в хранилище секретов, с доступом по принципу минимума.

ТЕОРИЯ: что нужно знать перед выполнением
Секрет должен жить вне кода: переменные окружения/CI-secrets для
сервисов, защищённое хранилище или константы с шифрованием для 1С,
локальный .env (в .gitignore, рядом .env.example без значений).
Код читает секрет в момент использования и не логирует его никогда:
ни в журнал, ни в ошибки, ни в «отладочные» сообщения.

Секрет, попавший в историю Git, скомпрометирован навсегда: его
ротируют (старый отзывают, новый выдают), а переписывание истории
почти никогда не является решением — клоны и кэши уже разошлись.

CI-проверка на утечки — сканер секретов перед слиянием: известный
формат ключей, высокая энтропия, тестовый секрет из задания обязан
её зажечь. Сканер не заменяет дисциплину, а ловит «случайно
закоммитил .env» — самую частую реальную причину.

Выдача и ротация — процесс с владельцем и периодичностью: кто
выдаёт, как передаётся (не по почте в открытом виде), где фиксируется
факт ротации. Доступ — по минимуму: сервису нужен только его секрет.

Проверка стражи: коммит с тестовым ключом формата партнёрского API —
CI падает до слияния, отчёт показывает файл и строку, но не сам секрет.
Типичные ошибки: ротировать секрет в коде, но забыть второй экземпляр
в CI-переменной (половина конвейера работает, половина нет); .env.example
заполнить настоящими значениями «для примера»; считать, что удалённый
из HEAD секрет спасён (история Git помнит всё).

Проверка понимания: разработчик говорит «секрет только в моём
локальном .env, в Git его нет». Чем вы это подтвердите за минуту —
и почему «я не коммитил» не является подтверждением?

Секрет, попавший в Git однажды, считается скомпрометированным
навсегда: удаление из текущего файла не чистит историю, лечится
только ротацией. Хранение делится на три среды с разными наборами
(dev/test/integration — task_262): утечка dev-секрета не открывает
продакшен. Проверка «секретов нет в репозитории» автоматизируется
сканером в CI (task_261/293), а не глазами на ревью: глаза
устают ровно на том коммите, где секрет и лежит. Ротация без
простоя — два активных значения, как в task_261.

ЗАДАНИЕ: что сделать
1. Проведите аудит: найдите в проекте все места, где хранятся секреты
   (пароли СУБД, ключи API, токены). Составьте список.
2. Перенесите секреты из кода и конфигурации в защищённое хранилище: константы с
   шифрованием / переменные окружения / CI-secrets.
3. Реализуйте в CI проверку на утечку секретов (scan перед коммитом).
4. Опишите процесс выдачи и ротации секретов: кто, как, с какой периодичностью.
5. Проверьте: в Git-истории нет секретов (если есть — опишите план устранения).

- Локальный .env удобен, но должен быть в .gitignore и иметь шаблон .env.example без значений.
