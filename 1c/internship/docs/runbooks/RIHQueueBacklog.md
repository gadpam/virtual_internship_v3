# RIHQueueBacklog

**Симптом:** сообщения накапливаются в очереди: заказы приняты магазином, но не
появились в 1С; бонусы не начислены; статусы доставки не обновились.
**Приоритет:** page
**Порог:** `rih_queue_depth{state="ready"}` > 500 сообщений дольше 5 минут
**Владелец:** дежурный инженер RIH

## Влияние

Данные **не потеряны** — они лежат в очереди. Но пользователь видит устаревшее
состояние: заказ «не проведён», бонусов нет, статус доставки прежний. Чем дольше
простой, тем больше риск, что сообщения уйдут в DLQ по исчерпанию повторов.

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Сколько и в каком состоянии
docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
  rabbitmqctl list_queues name messages messages_ready messages_unacknowledged consumers

# 2. Жив ли консьюмер
docker compose -f ../../tools/docker-compose.yml ps queue_consumer
docker compose -f ../../tools/docker-compose.yml logs --tail=100 queue_consumer

# 3. Куда упирается: ошибки по системам
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=sum by (system,code) (increase(rih_errors_total[10m]))'
```

## Диагностика

### `consumers == 0` — консьюмер не работает

* контейнер упал или перезапускается → логи, затем `docker compose restart queue_consumer`;
* консьюмер жив, но не подключился к брокеру → неверный `AMQP_URL` (task_261);
* консьюмер подключён, но `PREFETCH` исчерпан неотвеченными сообщениями
  (`messages_unacknowledged` большое, `ready` растёт) → зависшие обработки:
  перезапуск консьюмера вернёт сообщения в очередь.

### Консьюмер работает, но медленно

* партнёр отвечает с задержкой → смотрите `RIHLatencySLOBreach.md`;
* все сообщения уходят в повторы (5xx, таймауты) → `RIHPartnerUnavailable.md`;
* нагрузка выше расчётной → увеличить число консьюмеров **только после** проверки,
  что приёмная сторона выдержит (task_202).

### Очередь растёт только в одном направлении

Проверьте конкретный обмен: возможно, сломался один маршрут (неверный routing key),
и сообщения копятся в «мёртвой» очереди без консьюмера.

## Восстановление

1. Поднять консьюмер: `docker compose up -d queue_consumer`, дождаться `healthy`.
2. Наблюдать 10 минут: `rih_queue_depth{state="ready"}` должно снижаться.
   Команда для наблюдения:
   ```bash
   watch -n 15 'docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
     rabbitmqctl list_queues name messages messages_ready'
   ```
3. Если не снижается — причина не в консьюмере: см. диагностику выше.
4. После разбора очереди проверить целостность:
   * нет дублей (идемпотентность по `external_id` / `operation_id`, task_105);
   * нет потерянных сообщений: число принятых = число обработанных + DLQ;
   * порядок соблюдён там, где он важен (task_112).
5. Сообщить бизнесу фактическое время отставания: «заказы за период 09:12–09:40
   обработаны в 10:05».

## Чего делать нельзя

* **Не удалять сообщения** (`purge`), чтобы «очистить алерт»: это потеря заказов.
* **Не увеличивать `MAX_RETRIES` до бесконечности**: бесконечные повторы при
  неработающем партнёре создают лавину.
* **Не запускать второй консьюмер на ту же очередь**, если причина в зависших
  блокировках на стороне 1С: станет хуже.

## Эскалация

| Когда | Кому |
|---|---|
| сразу | дежурный инженер RIH |
| 15 минут без снижения | владелец интеграции |
| 30 минут или очередь > 5000 | руководитель разработки, уведомление магазина |
| сообщения уходят в DLQ пачками | как `RIHDeadLetterGrowing` + этот алерт |

## После инцидента

* метрики: максимальная глубина, время разбора, сколько сообщений ушло в DLQ;
* действие на обнаружение: алерт на `consumers == 0` срабатывает раньше, чем
  глубина очереди (добавить в `alert_rules.yml`, task_272);
* действие на восстановление: автоматический рестарт консьюмера, healthcheck
  с проверкой подключения к брокеру.
