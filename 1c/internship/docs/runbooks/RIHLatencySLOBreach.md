# RIHLatencySLOBreach

**Симптом:** операции выполняются, но медленно: пользователь ждёт проведения
заказа, страница магазина обновляется с задержкой.
**Приоритет:** ticket (не page: сервис работает)
**Порог:** p95 `rih_integration_duration_seconds` > 2 с за 10 минут
**Владелец:** разработчик RIH + дежурный

## Влияние

Пользователь видит «система тормозит». Риск важнее симптома: рост латентности —
обычно предвестник отказа (исчерпание пула соединений, рост очереди, деградация
СУБД). Обработка алерта сегодня экономит page ночью.

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Какая система и операция тормозит
curl -s http://localhost:9090/api/v1/query --data-urlencode \
  'query=histogram_quantile(0.95, sum by (le,system,operation) (rate(rih_integration_duration_seconds_bucket[10m])))'

# 2. Глубина очереди: латентность часто объясняется ожиданием, а не работой
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=rih_queue_depth'

# 3. Нагрузка: не вырос ли RPS
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=sum by (system) (rate(rih_integration_requests_total[5m]))'
```

## Диагностика

### p95 вырос вместе с нагрузкой

Это ожидаемая деградация. Проверьте по профилю нагрузки (`tests/load/scenarios/README.md`),
на каком RPS система уходит за 2 с. Если рабочая нагрузка близка к этой точке —
нужен capacity planning (task_202), а не оптимизация запроса.

### p95 вырос без изменения нагрузки

* **СУБД**: блокировки и долгие запросы — `tools/sql/diagnostics/010_who_is_active.sql`,
  `020_blocking_chain.sql`, `030_query_store_report.sql` (task_184, task_187);
* **внешний вызов**: партнёр стал отвечать медленнее — сравните длительность по
  `system`;
* **пул соединений**: исчерпан, запросы ждут свободного соединения (task_191);
* **новый код**: посмотрите последние релизы — `git log --oneline -10`, сопоставьте
  время начала деградации с временем установки (task_268).

### Тормозит одна операция

Смотрите её план и объём данных. Типичные причины в 1С: запрос в цикле, получение
объекта вместо ссылки, отсутствие индекса, виртуальная таблица без параметров
(стандарт §3, §6).

## Восстановление

1. Если причина — партнёр: уведомить, включить деградацию (кеш, очередь), ждать.
2. Если причина — СУБД: снять блокировку (`kill session` только по согласованию
   с администратором СУБД), обновить статистику, добавить индекс **по ADR**
   (task_188, task_195).
3. Если причина — наш код: откат релиза быстрее, чем оптимизация под нагрузкой.
4. После восстановления — замер «до/после» в отчёте (`tests/load/`, task_192):
   утверждение «стало быстрее» без цифр не принимается.

## Эскалация

| Когда | Кому |
|---|---|
| в течение рабочего дня | разработчик, отвечающий за контур |
| p95 > 5 с или растёт | дежурный инженер + владелец интеграции |
| латентность привела к таймаутам у пользователей | как `RIHPartnerUnavailable` (page) |

## После инцидента

* запись в реестр технического долга, если причина в коде (`backlog/tech_debt_register.md`,
  task_220);
* нагрузочный сценарий, воспроизводящий профиль (task_201);
* пересмотр SLO, если 2 с недостижимы по объективным причинам — но только через
  согласование с потребителем (task_271), а не молча.
