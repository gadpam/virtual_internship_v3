# RIHDeadLetterGrowing

**Симптом:** сообщения, которые не удалось обработать, копятся в DLQ. Пользователь
этого не видит — и именно поэтому алерт опасен: часть операций молча не выполнена.
**Приоритет:** ticket
**Порог:** прирост `rih_queue_depth{queue="rih.orders.in.dlq"}` > 10 сообщений
за 15 минут
**Владелец:** разработчик RIH + дежурный

## Влияние

Каждое сообщение в DLQ — невыполненная бизнес-операция: заказ не проведён, бонусы
не начислены, статус доставки не обновлён. Данные есть, но они **никому не видны**,
пока их не разобрали.

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Сколько в DLQ
docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
  rabbitmqctl list_queues name messages | grep dlq

# 2. Смотрим первое сообщение и причину (без удаления!)
docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
  rabbitmqadmin get queue=rih.orders.in.dlq count=3 ackmode=ack_requeue_true

# 3. Журнал консьюмера вокруг времени попадания
docker compose -f ../../tools/docker-compose.yml logs --since 30m queue_consumer \
  | grep -iE "dlq|dead|retry"
```

## Диагностика: почему сообщение попало в DLQ

Таблица решений консьюмера (`src/queue_consumer/README.md`):

| Причина | Признак в заголовках | Что делать |
|---|---|---|
| исчерпаны повторы (`x-retry-count >= 3`) | `x-retry-count: 3` | партнёр был недоступен: повторить обработку после восстановления |
| ошибка данных 4xx | `x-death-reason: rejected`, код 400/422 | сообщение некорректно: исправлять данные, не повторять |
| неизвестный формат | ошибка парсинга в логе | контракт изменился: `pytest -q contract`, `docs/api/` |
| ошибка в нашем коде | traceback в логе | дефект: исправить, затем разобрать DLQ |

**Правило:** сначала причина, потом разбор. Повторная отправка сообщения с ошибкой
данных создаст второй такой же труп.

## Разбор DLQ

1. Выгрузить сообщения в файл (не удаляя из очереди):
   ```bash
   docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
     rabbitmqadmin get queue=rih.orders.in.dlq count=100 ackmode=ack_requeue_true \
     > ../../build/dlq/dlq_$(date +%Y%m%d_%H%M).json
   ```
2. Классифицировать: сколько по каждой причине (таблица выше).
3. Для «партнёр был недоступен» — вернуть в основную очередь после восстановления
   партнёра; идемпотентность гарантирует, что дублей не будет (task_105).
4. Для ошибок данных — завести задачу в трекере на исправление источника
   (кто прислал такие данные) и обработать вручную.
5. Для дефектов кода — исправить, покрыть тестом (`tests/integration/test_fault_handling.py`),
   затем разобрать.
6. Записать результат: сколько сообщений разобрано, сколько осталось, почему.

## Чего делать нельзя

* **Не очищать DLQ** ради «чистого дашборда».
* **Не возвращать всё скопом** без понимания причины: при ошибке данных вы
  получите ту же ошибку и ту же DLQ, но уже с потерей порядка (task_112).

## Эскалация

| Когда | Кому |
|---|---|
| в рабочий день | разработчик контура |
| DLQ > 100 сообщений или растёт непрерывно | дежурный + владелец интеграции |
| в DLQ критичные операции (платежи, заказы) | как page: руководитель разработки |

## После инцидента

* реестр: сколько сообщений, причины, время в DLQ, как разобраны;
* действие на предотвращение: валидация на входе, контрактный тест на изменившуюся
  схему, алерт на конкретный код ошибки;
* если причина «исчерпаны повторы при сбое партнёра» — проверить, что алерт
  `RIHPartnerUnavailable` сработал раньше, чем сообщения попали в DLQ (task_272).
