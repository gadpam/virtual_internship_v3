# RIHPartnerUnavailable

**Симптом:** партнёр (магазин, лояльность, ТК, банк, трекер) массово отвечает
ошибкой или таймаутом; операции уходят в повторы и в DLQ.
**Приоритет:** page
**Порог:** доля ответов 5xx и таймаутов > 20% за 5 минут по одной внешней системе
**Владелец:** дежурный инженер RIH

## Влияние

Зависит от партнёра:

| Партнёр | Что деградирует | Данные теряются? |
|---|---|---|
| SHOP | приём заказов, выгрузка остатков | нет: магазин копит заказы у себя |
| LOYA | начисление и списание бонусов | нет: операции в очереди |
| TK | расчёт и заявки доставки | частично: цена считается по кешу тарифов |
| BANK | выписка, платежи, курсы | нет: платежи ждут, курсы из кеша |
| TRK | создание инцидентов | нет: задачи в очереди |

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Жив ли партнёр вообще (health без авторизации)
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://localhost:8080/shop/health
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://localhost:8080/loyalty/health
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://localhost:8080/tk/health

# 2. Что в очереди и в DLQ
docker compose -f ../../tools/docker-compose.yml exec rabbitmq \
  rabbitmqctl list_queues name messages messages_ready messages_unacknowledged

# 3. Ошибки по системам за последние минуты
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=sum by (system,code) (increase(rih_errors_total[5m]))'
```

## Диагностика

### Партнёр отвечает, но с ошибкой

* `500` на всех операциях → сбой на стороне партнёра: уведомить его дежурного,
  включить режим ожидания;
* `401`/`403` → истёк или изменён ключ: **не повторять** (повторы только умножат
  ошибки), проверить `.env` и согласовать ключ с партнёром (task_134, task_261);
* `422`/`400` → изменился контракт: сравнить схему в `docs/api/` с фактическим
  ответом, прогнать `pytest -q contract`;
* `429` → это не сбой, а лимит партнёра: проверить, не расходует ли RIH лимит
  опросом статуса (task_93).

### Партнёр не отвечает (таймаут)

* проверьте таймауты клиента: если партнёр отвечает за 8 с, а таймаут 5 с —
  «сбой» на нашей стороне (task_127);
* circuit breaker открыт → повторять бессмысленно, ждать полуоткрытого состояния
  и пробного запроса (task_129);
* nginx отдаёт `504` раньше клиента → увеличить `proxy_read_timeout` для этого
  маршрута **после** того, как согласован таймаут клиента.

### Ошибки только у части операций

Смотрите разрез по `operation` в `rih_integration_requests_total`: если одна
операция падает, а другие работают, причина в данных или в конкретной ручке
партнёра, а не в доступности.

## Восстановление

1. **Не увеличивайте число повторов** — это добивает партнёра и продлевает сбой.
2. Убедитесь, что circuit breaker работает: новые вызовы не уходят, очередь копится.
3. Уведомите партнёра: время начала, доля ошибок, какие операции затронуты.
4. Когда партнёр восстановился, очередь разбирается автоматически. Проверьте:
   `rih_queue_depth{state="ready"}` снижается, `rih_errors_total` не растёт.
5. Разберите DLQ (`RIHDeadLetterGrowing.md`): часть сообщений могла исчерпать повторы.
6. Проверьте идемпотентность: нет ли задвоенных начислений и документов за период сбоя.

## Эскалация

| Когда | Кому |
|---|---|
| сразу | дежурный инженер RIH |
| сразу | дежурный партнёра (контакт — `docs/api/integration_catalog.md`) |
| 20 минут без восстановления | владелец интеграции |
| 1 час | руководитель разработки + уведомление бизнеса о деградации |

## После инцидента

* таймлайн, гипотезы и доказательства — в отчёт (task_274);
* если партнёр менял контракт без предупреждения — письмо о порядке уведомлений
  и предложение версионирования (`documentation/templates/BusinessLetterTemplate.md`);
* если причина в наших таймаутах/ретраях — правка кода и нагрузочный тест на этот
  профиль (task_201).
