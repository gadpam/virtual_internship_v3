# Runbooks: что делать при алерте

Runbook — инструкция для дежурного, который видит алерт **впервые**. Хороший
runbook отвечает на три вопроса: что случилось с пользователем, как это проверить,
что сделать, чтобы стало лучше. Задания: task_272 (алерты), task_273 (дежурство),
task_274 (расследование).

## Индекс

| Алерт | Симптом | Приоритет | Runbook |
|---|---|---|---|
| `RIHIntegrationDown` | сервис интеграции не отвечает | page | [`RIHIntegrationDown.md`](RIHIntegrationDown.md) |
| `RIHPartnerUnavailable` | партнёр массово отвечает ошибкой | page | [`RIHPartnerUnavailable.md`](RIHPartnerUnavailable.md) |
| `RIHLatencySLOBreach` | p95 выше 2 с | ticket | [`RIHLatencySLOBreach.md`](RIHLatencySLOBreach.md) |
| `RIHQueueBacklog` | очередь не разбирается | page | [`RIHQueueBacklog.md`](RIHQueueBacklog.md) |
| `RIHDeadLetterGrowing` | растёт DLQ | ticket | [`RIHDeadLetterGrowing.md`](RIHDeadLetterGrowing.md) |
| `RIHExchangeLag` | обмен отстаёт от расписания | ticket | [`RIHExchangeLag.md`](RIHExchangeLag.md) |

Определения алертов: `tools/ci/observability/alert_rules.yml` (пороги обязаны
совпадать с таблицами в runbook — расхождение означает, что кто-то изменил порог
и не обновил инструкцию).

## Структура каждого runbook

1. **Симптом** — что видит пользователь (не «упал Prometheus»).
2. **Влияние** — какие процессы остановлены, что копится.
3. **Быстрая проверка** — 3–5 команд, которые за минуту показывают, где проблема.
4. **Диагностика** — ветвления: если А, то Б.
5. **Восстановление** — шаги в порядке от безопасных к рискованным.
6. **Эскалация** — кому и через сколько минут.
7. **После инцидента** — что записать, какие действия завести.

## Правила

* **Команды копируются и выполняются.** «Проверьте очередь» — не шаг; шаг —
  `rabbitmqctl list_queues name messages messages_ready messages_unacknowledged`.
* **Время в шагах явно**: «если за 10 минут не восстановилось — эскалация».
* **Никаких деструктивных действий без подтверждения**: удаление сообщений,
  очистка таблиц, перезапуск СУБД — только по согласованию с владельцем.
* **Runbook обновляется после каждого инцидента.** Если дежурный делал шаг,
  которого нет в инструкции, — шаг добавляется в тот же день (task_275).
* **Проверка раз в квартал**: учебный прогон по runbook на тестовом стенде
  (практика из task_132 — учение по сбою).

```markdown
# <AlertName>

**Симптом:** <что видит пользователь>
**Приоритет:** page | ticket
**Владелец:** <роль>
**Порог:** <условие из alert_rules.yml>

## Влияние
## Быстрая проверка (≤ 1 минуты)
## Диагностика
## Восстановление
## Эскалация
## После инцидента
```
