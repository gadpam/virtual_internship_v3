# RIHIntegrationDown

**Симптом:** сервис интеграции не отвечает — заказы из магазина не принимаются,
обмены стоят.
**Приоритет:** page (дежурный немедленно)
**Порог:** `rih_up == 0` дольше 2 минут для любого сервиса
(`tools/ci/observability/alert_rules.yml`)
**Владелец:** дежурный инженер RIH

## Влияние

| Что остановлено | Через сколько станет заметно |
|---|---|
| приём заказов из магазина | сразу: магазин копит заказы у себя |
| начисление бонусов | сразу, но данные в очереди не теряются |
| выгрузка каталога и остатков | через 15 минут: цены в магазине устаревают |
| обмен с банком и бухгалтерией | в конце дня: сверка не сходится |

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Что именно не отвечает
curl -s http://localhost:8080/healthz | python3 -m json.tool

# 2. Состояние контейнеров
docker compose -f ../../tools/docker-compose.yml ps

# 3. Последние логи упавшего сервиса
docker compose -f ../../tools/docker-compose.yml logs --tail=100 <service>
```

## Диагностика

### Сервис не запущен / перезапускается

* в логах `OOMKilled` или `exit code 137` → не хватает памяти: смотрите
  `docker stats`, поднимите лимит или отключите тяжёлые сервисы;
* в логах ошибка конфигурации (`KeyError`, `ValidationError`, `Address already in use`)
  → изменения в `.env` или `docker-compose.yml`: откатите последний коммит
  (`git log -3 -- ../../tools`), поднимите снова;
* сервис «restarting» циклически → healthcheck не проходит: проверьте, что
  порт и путь healthcheck совпадают с фактическими.

### Сервис запущен, но не отвечает

* `docker compose exec <service> curl -s localhost:<port>/health` — если внутри
  отвечает, а снаружи нет, проблема в nginx или в сети;
* логи nginx: `docker compose logs --tail=100 nginx | grep -E "502|504|upstream"`;
* `UPSTREAM_UNAVAILABLE` в ответе nginx → контейнер жив, но процесс не слушает:
  перезапуск сервиса;
* nginx отвечает `403` для `/metrics` → это норма (allow-list внутренней сети),
  не инцидент.

### Упала вся инфраструктура

* СУБД или RabbitMQ недоступны → все сервисы деградируют одновременно. Порядок
  восстановления: `postgres` → `rabbitmq` → `nginx` → сервисы. Проверка:
  `docker compose ps` и `rabbitmq-diagnostics -q ping`.

## Восстановление

1. Перезапустить сервис: `docker compose restart <service>` и дождаться
   `healthy` (`docker compose ps`).
2. Проверить `curl -s http://localhost:8080/healthz`.
3. **Разобрать накопившиеся сообщения**: `RIHQueueBacklog.md`, шаги восстановления.
4. Проверить, что данные не задвоились: журнал интеграций за период простоя —
   нет ли двух документов с одним `externalId`.
5. Сообщить магазину и дежурному лояльности о периоде простоя и о том, что
   операции будут доставлены повторно.

## Эскалация

| Когда | Кому |
|---|---|
| сразу | дежурный инженер RIH (page) |
| не восстановлено за 15 минут | владелец интеграции + руководитель разработки |
| не восстановлено за 30 минут | ИТ-директор, уведомление коммерческой службы |
| простой дольше 1 часа | уведомление партнёров письмом (`documentation/templates/BusinessLetterTemplate.md`) |

## После инцидента

1. Таймлайн и гипотезы — в отчёт об инциденте
   (`documentation/templates/IncidentReportTemplate.md`).
2. Если простой дольше 30 минут или потеряны данные — postmortem
   (`documentation/templates/PostmortemTemplate.md`, task_275).
3. Действия: минимум одно на предотвращение, одно на обнаружение, одно на
   ускорение восстановления.
4. Обновить этот runbook, если какого-то шага в нём не было.
