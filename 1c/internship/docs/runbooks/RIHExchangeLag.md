# RIHExchangeLag

**Симптом:** плановый обмен отстаёт от расписания: данные в 1С или в витринах
старее, чем должны быть. Пользователь видит вчерашние остатки и несвежие цифры
в отчётах.
**Приоритет:** ticket
**Порог:** `rih_exchange_lag_seconds` > 900 с (15 минут) для любого плана обмена
**Владелец:** дежурный инженер RIH + владелец данных (для витрин)

## Влияние

| Направление | Что устаревает | Терпимо |
|---|---|---|
| каталог и цены в магазин | цены, остатки | 15–30 минут |
| заказы в 1С | проведение заказов | 5 минут |
| факты в витрины (`fact_integration`) | дашборд интеграций | 15 минут |
| продажи в витрины (`fact_sales`) | отчёты за день | T+1 до 06:00 |
| курсы валют | пересчёт валютных цен | 24 часа |

SLA свежести целиком: `tools/bi/freshness_sla.md` (task_210).

## Быстрая проверка (≤ 1 минуты)

```bash
# 1. Какой план обмена отстаёт
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=rih_exchange_lag_seconds'

# 2. Свежесть витрин
docker compose -f ../../tools/docker-compose.full.yml exec postgres \
  psql -U rih -d rih -c "SELECT * FROM marts.v_freshness;"

# 3. Состояние регламентных заданий и ETL-прогонов
docker compose -f ../../tools/docker-compose.full.yml exec postgres \
  psql -U rih -d rih -c "SELECT run_id, pipeline, status, started_at, finished_at FROM staging.etl_runs ORDER BY started_at DESC LIMIT 10;"
```

## Диагностика

### Обмен в 1С не запустился

* регламентное задание выключено или заблокировано (после релиза задания часто
  остаются выключенными — проверьте первым делом, task_113);
* сеанс задания завершается с ошибкой: журнал регистрации за период;
* расписание сдвинулось после перехода на летнее время или изменения TZ
  (task_15, `TZ=Europe/Minsk` в `.env`).

### Обмен запустился, но не завершился

* большое количество изменений: обмен «догоняет» очередь — смотрите
  `RIHQueueBacklog.md`;
* блокировка данных: ТИИ или обновление конфигурации держат базу (task_197);
* партнёр недоступен: `RIHPartnerUnavailable.md`.

### Отстают витрины

* ETL-прогон упал: `staging.etl_runs.status = 'failed'` → смотреть сообщение и
  правила качества (`tools/sql/etl/020_dq_rules.sql`): партия блокируется, если
  доля брака выше 5% (task_212);
* прогон не запускался: расписание или недоступность источника;
* источник пуст: выгрузка из 1С не сформировалась — проверять надо обмен, а не ETL.

## Восстановление

1. Устранить причину (запустить задание, снять блокировку, починить ETL).
2. Запустить обмен/прогон вручную и дождаться завершения; для ETL — убедиться,
   что повторный прогон идемпотентен: `etl_runs` показывает один успешный прогон
   за период, а не два набора фактов (task_211).
3. Проверить, что отставание вернулось в норму: `rih_exchange_lag_seconds` < 900.
4. Обновить баннер свежести на дашборде (если он показывает период простоя —
   оставить его до момента, когда данные станут полными, task_210).
5. Сообщить потребителям фактический период устаревания данных: «остатки на 09:40
   актуальны по 09:12».

## Эскалация

| Когда | Кому |
|---|---|
| в рабочий день | владелец обмена / владелец данных |
| отставание > 1 часа | дежурный инженер |
| нарушен SLA T+1 06:00 для `fact_sales` | владелец данных + руководитель разработки до начала рабочего дня |
| отставание затрагивает кассу или банк | page: как критичный инцидент |

## После инцидента

* зафиксировать фактическое время восстановления и нарушенный SLA (для отчётности
  по доступности данных, task_210);
* если причина «задание не запустилось после релиза» — пункт в план релиза
  (`documentation/templates/ReleasePlanTemplate.md`: включить регламентные задания
  и проверить первый прогон);
* если причина в качестве данных — правило DQ, которое должно было заблокировать
  партию раньше (task_212).
