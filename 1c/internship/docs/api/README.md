# Документация API и интеграций RIH

Единая точка, откуда партнёр, коллега и вы сами через полгода узнаёте, **как
устроен обмен**. Документация API живёт рядом с кодом и обновляется тем же
коммитом, что и контракт (task_77, task_82, task_96).

## Правила ведения

1. **Источник истины — OpenAPI.** Для сервисов на FastAPI схема генерируется
   автоматически (`/openapi.json`), но наружу она закрыта nginx
   (`/docs`, `/redoc`, `/openapi.json` → 403). Партнёру отдаём **экспортированный
   файл** из `internship/build/api/`, а не ссылку на стенд.
2. **Описание в Markdown дополняет схему**, а не дублирует её: здесь живут
   семантика, идемпотентность, лимиты, поведение при сбое, примеры.
3. **Любое изменение контракта — отдельный коммит** с обновлением документации и
   контрактных тестов (`tests/contract/`). Изменение без теста = изменение без гарантии.
4. **Версия в пути** (`/api/v1/`). Ломающие изменения — только в новой версии;
   старая живёт до окончания переходного периода (task_82, task_267).
5. **Каждая интеграция имеет владельца** — роль и имя, а не «команда». Без владельца
   интеграция умирает молча.

## Что обязательно описано для каждого контракта

* назначение и бизнес-владелец;
* транспорт, авторизация, окружения (dev/test/integration);
* методы и поля: тип, обязательность, ограничения, пример;
* идемпотентность: какой ключ, что происходит при повторе;
* лимиты: частота, объём, `Retry-After`;
* ошибки: коды и что делать вызывающей стороне;
* поведение при сбое: таймаут, повтор, деградация, компенсация;
* журнал: куда пишутся вызовы и как их найти по `correlationId`.

## Как проверить, что документация не разошлась с кодом

```bash
cd 1c/internship/tests
pytest -q contract            # контрактные тесты сверяют документацию с поведением
```

Контрактный тест — исполнительный документ. Если в тесте поля нет, а в документации
есть (или наоборот), прогон красный: расхождение найдено автоматически.
