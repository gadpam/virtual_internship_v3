# Карта интеграций RIH (task_73, task_120)

Реестр всех обменов холдинга. Отвечает на четыре вопроса: **кто с кем**, **что
передаёт**, **кто отвечает**, **что будет, если обмен встанет**.

## Системы ландшафта

| Код | Система | Роль в обмене | Протокол | Владелец |
|---|---|---|---|---|
| `RIH` | Retail Integration Hub (1С 8.3) | центр интеграции, источник истины по заказам и НСИ | — | команда RIH |
| `SHOP` | Онлайн-магазин | каталог, заказы, остатки | HTTP/JSON | команда магазина |
| `LOYA` | Программа лояльности | карты, баллы, сторно | HTTP/JSON | команда лояльности |
| `TK` | Транспортная компания | расчёт доставки, заявки, этикетки | HTTP/JSON | логистика + ТК |
| `BANK` | Банк | выписка, платёжные поручения, курсы валют | SOAP/HTTPS | казначейство |
| `TRK` | Внешний трекер задач | инциденты, процессы, SLA | HTTP/JSON | ИТ-служба |
| `BP` | Бухгалтерия предприятия | проводки, сверка | план обмена / HTTP | бухгалтерия |
| `DO` | Документооборот | договоры, согласования | HTTP/JSON | делопроизводство |
| `BI` | Витрины и Superset | аналитика | SQL/PostgreSQL | команда данных |
| `MOB` | Мобильное приложение | офлайн-операции, сканер | HTTP/JSON + очередь | команда RIH |

## Способ обмена и почему

| Поток | Синхронно / асинхронно | Обоснование |
|---|---|---|
| заказы SHOP → RIH | асинхронно (очередь) | магазин не должен ждать проведения документа; сбой RIH не теряет заказ |
| начисление баллов | асинхронно с ретраем | лояльность часто недоступна; операция обязана доставиться ровно один раз |
| расчёт доставки | синхронно | ответ нужен пользователю здесь и сейчас; при сбое — деградация |
| курсы валют | синхронно + кеш 24 ч | данные меняются раз в день, кеш снимает нагрузку (task_94) |
| платёжное поручение | синхронно + журнал | нужен немедленный результат и юридически значимый след |
| факты в BI | асинхронно (ETL) | аналитике важна полнота, а не миллисекунды |

| Поток | Доступность | p95 | Отставание | Что при нарушении |

## Как поддерживать реестр живым

1. Новая интеграция появляется в реестре **до** первой строчки кода.
2. Раз в квартал сверка: какие потоки реально ходят (по журналу интеграций) и
   какие описаны. Расхождение — либо мёртвая запись, либо теневой обмен.
3. У каждого потока есть владелец и заместитель. Отпуск владельца без заместителя
   останавливает согласования.
4. Изменение SLA согласуется с потребителем письменно (шаблон:
   `documentation/templates/BusinessLetterTemplate.md`).
