# Витрины данных для BI (task_205, task_206, task_208)

**Диалект: PostgreSQL** (не T-SQL!). Каталог `marts/` монтируется в контейнер
PostgreSQL как `/docker-entrypoint-initdb.d`, поэтому скрипты выполняются
автоматически при первом старте тома — и должны быть идемпотентными
(`CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE VIEW`).

| Файл | Что создаёт |
|---|---|
| `010_schema.sql` | схему `marts`, справочники измерений |
| `020_mart_sales.sql` | витрину продаж `marts.fact_sales` с измерениями |
| `030_mart_integration.sql` | витрину интеграций `marts.fact_integration` (основа дашборда SLO) |
| `040_metrics_dictionary.sql` | представление-словарь метрик: формула, источник, владелец |
| `050_quality_views.sql` | представления качества данных и свежести витрин |

## Почему витрины отдельным слоем

Отчёт 1С отвечает на вопрос пользователя в моменте. BI-дашборд, сверка, KPI
план-факт и самообслуживание аналитиков работают быстрее и предсказуемее поверх
**витрины**, которая:

1. собрана один раз и не пересчитывает исходные регистры на каждый запрос;
2. имеет явные измерения (дата, магазин, товар, контрагент) и факты (суммы, количества);
3. имеет владельца, SLA свежести и словарь метрик;
4. не даёт аналитикам «изобрести» свою версию выручки — формула зафиксирована в `040`.

Граница ответственности: 1С — источник истины по операциям; витрина — согласованная
версия цифр для управления. Расхождение между ними — инцидент качества данных (task_212),
а не «разные системы считают по-разному».

