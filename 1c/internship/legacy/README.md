# Легаси-код для рефакторинга (task_217–222)

Здесь лежит «наследие», которое вы будете разбирать, покрывать тестами и
переписывать. Оно намеренно плохое: длинная процедура, вложенные условия,
магические числа, бизнес-правила внутри цикла, отсутствие комментариев. Так
выглядит реальный код, который достался от подрядчика пять лет назад.

| Файл | Что это |
|---|---|
| `LegacyPriceModule.bsl` | модуль расчёта цены для обмена с магазином: 1 процедура на ~150 строк |
| `legacy_rules.py` | точный порт поведения модуля на Python — опора для characterization-тестов |
| `NOTES.md` | что уже известно о модуле: гипотезы, вопросы к владельцу, находки |

## Порядок работы (совпадает с заданиями)

1. **task_217 — разбор.** Прочитать модуль, составить карту: входы, выходы,
   ветвления, побочные эффекты. Записать в `NOTES.md` вопросы, на которые код
   не отвечает («почему скидка 7% именно при сумме больше 500?»).
2. **task_218 — characterization-тесты.** Зафиксировать текущее поведение
   тестами, включая странности и баги. Тест описывает то, что есть, а не то,
   что должно быть. Прогоны: `tests/legacy/test_characterization.py`.
3. **task_219 — рефакторинг малыми шагами.** Один шаг = одно изменение = зелёные
   тесты. Порядок: имена → выделение функций → удаление вложенности → таблицы
   вместо if-каскадов.
4. **task_220 — реестр технического долга.** Что нашли, какова цена, какой риск,
   в каком порядке чинить.
5. **task_221 — стандарты.** Привести модуль к `Configuration/Docs/CodingStandard.md`
   и проверить линтером `src/scripts/lint_bsl.py`.
6. **task_222 — документация.** Описать правила расчёта цены так, чтобы их понял
   человек, который никогда не открывал этот модуль.

## Правило курса

**Не исправляйте баги до того, как зафиксировали поведение тестами.** Если
«очевидная ошибка» на самом деле является бизнес-правилом (а в легаси так бывает
часто), вы молча сломаете расчёт цен. Сначала тест, потом вопрос владельцу,
потом изменение — отдельным коммитом с объяснением.
