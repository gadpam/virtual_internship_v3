> Файл-заготовка. Заполняется в заданиях task_6 (именование), task_10 (стандарты 1С),
> task_12 (статический анализ), task_18 (запросы), task_44 (транзакции), task_45 (блокировки),
> task_51 (ошибки), task_127 (таймауты), task_134 (секреты).
> Объём документа — 1–2 страницы. Всё, что не помещается, выносите в отдельные разделы документации.

## 1. Имена (task_6)

| Категория | Правило | Пример | Плохой пример |
|---|---|---|---|
| Объекты метаданных | Префикс подсистемы `РИХ_` для общих модулей, обработок, ролей, сервисов | `РИХ_МониторингОбменов` | `Обработка1`, `MyProc` |
| Переменные | С заглавной буквы, существительное, без сокращений | `ТаблицаОстатков` | `t_ost`, `x` |
| Методы | Глагол + объект | `РассчитатьСебестоимость()` | `Calc()`, `Обработка()` |
| Параметры | С заглавной буквы, тип не в имени | `ДатаНачала` | `p_date`, `strName` |
| Константы | ВЕРХНИЙ_РЕГИСТР, объявлены в области констант модуля | `МАКС_РАЗМЕР_ПАКЕТА` | `maxSize` |
| Роли | `РИХ_<Роль>` | `РИХ_Кладовщик` | `Роль1` |

Уточнения для RIH (task_6; проверка стартера нарушений не нашла — стартовые
модули `РИХ_Дата`, `РИХ_ОбщегоНазначения`, `РИХ_HTTP1_Ответы` конвенции
соответствуют, переименовывать их нельзя: на имена ссылаются задания
программы):

1. **Цифры в именах запрещены.** Существующее имя `РИХ_HTTP1_Ответы` —
   легаси стартера и единственное исключение; новые модули именуются
   словами (`РИХ_HTTPОтветы` — если бы создавали сегодня).
2. **Проверка имени за пять секунд.** По имени метода читающий понимает,
   что он делает и что вернёт, не открывая тело. Экспортные функции
   серверных модулей, отдающие отчёт вызывающему, называются глаголом
   (`ПроверитьОкружение()`) и возвращают строку/структуру, а не
   показывают сообщение сами.
3. **Префикс `РИХ_` обязателен** для: общих модулей, обработок, ролей,
   HTTP- и веб-сервисов своей подсистемы. Типовым объектам и объектам
   чужих подсистем префикс не ставится: префикс — граница ответственности,
   а не украшение.

## 2. Структура модуля (task_10)

```
// Заголовок: назначение модуля, правила, история заданий
#Область ПрограммныйИнтерфейс     // экспортные методы, каждый с документацией
#Область СлужебныеПроцедурыИФункции
#Область СлужебныеОбработчикиСобытий
#Область Инициализация
#Область КонструкторыФорм / ОбработчикиСобытий (для модулей форм)
```

Правила:
- экспортный метод обязан иметь документацию: назначение, параметры, возвращаемое значение;
- модуль не длиннее ~500 строк: больше — выносите в отдельные модули по ответственности;
- логика живёт в общих модулях, а не в формах и обработчиках проведения (task_43).

## 3. Запросы (task_18)

- параметры передаются параметрами (`&Имя` + `УстановитьПараметр`),
  конкатенация значений в текст запроса запрещена без исключений:
  пользовательский ввод — данные, а не код (инъекция), а статический
  текст платформа компилирует один раз и переиспользует;
- ключевые слова ВЕРХНИМ РЕГИСТРОМ, отступы 1 таб, каждое поле и каждое
  условие — с новой строки: запрос читается как текст и ревьюится;
- временные таблицы именуются `Вт<Содержимое>` (например, `ВтОстаткиНаДату`),
  индексы временных таблиц объявляются явно;
- виртуальные таблицы всегда с параметрами периода/момента времени
  и отборов в скобках, а не «выбрать всё и отфильтровать потом»;
- запрос в цикле запрещён (исключение — обосновать комментарием и ADR);
- написал запрос — посмотрел его план и время на объёме, а не только
  «вернул правильный ответ на трёх тестовых записях» (глубоко — Q3);
- виртуальная таблица остатков/среза внутри сложного запроса без отборов
  по её измерениям — плохая идея (task_26): платформа пересчитает движения
  под каждый вызов. Правило: вирт. таблицу вызываем один раз с отборами
  в параметрах, результат — во временную таблицу с индексом, дальше
  пакет работает по ней. Исключение — одиночный простой запрос отчёта,
  где вирт. таблица и есть весь запрос;
- соединение с историей (регистром без среза) запрещено: размножает
  строки по числу записей истории. Нужна «цена на дату» — только срез.

## 4. Транзакции и блокировки (task_44, task_45)

- Явная транзакция — только для группы записей, которые обязаны жить
  или умереть вместе (загрузка + протокол). Проведение документа свою
  транзакцию уже имеет: явная внутри проведения запрещена.
- Транзакция короткая: внутри запрещены внешние вызовы (HTTP, файлы,
  ожидание пользователя) — вызов держит блокировки и превращает чужую
  медлительность в наши висячие транзакции (подробно — рефлексия task_44).
- В `Исключение` обязательна отмена транзакции и повторный вызов ошибки:
  проглоченная ошибка внутри транзакции = зафиксированный мусор.
- Блокировки (task_45): управляемые; захват всегда в одном порядке —
  сначала склад, затем номенклатура по возрастанию артикула: одинаковый
  порядок у всех сеансов делает deadlock невозможным по построению.
  Ожидание блокировки — с таймаутом и сообщением пользователю словами,
  а не молчаливым зависанием формы.

## 5. Обработка ошибок (task_51)

Классификация: ошибка пользователя (неверные данные — сообщение на поле,
без журнала ошибок), ошибка данных (битый файл — журнал + повтор/пропуск
по политике источника), ошибка системы (недоступен сервис — журнал, ID
инцидента пользователю, повторный вызов там, где операция не завершена).

- внешние вызовы — в `Попытка/Исключение` с логированием и `incidentId`;
- пользователю — короткий текст и действие («Не удалось загрузить прайс.
  Обратитесь в поддержку, инцидент <ID>»); в журнал — полный контекст
  через РИХ_Логирование.ЗаписатьОшибку;
- пустой блок `Исключение` запрещён; «проглотить и продолжить» допустимо
  только с записью в журнал и комментарием, почему продолжение безопасно;
- внутри транзакции исключение = отмена + повторный вызов (раздел 4),
  а не фиксация остатка работы.

## 6. Производительность (task_36, task_56, task_187+)

- изменения производительности — только с замером «до/после»;
- пакетная запись движений и данных;
- индексы добавляются обоснованно (ADR), с оценкой цены записи.

Чек-лист «отчёт тормозит: 7 первых проверок» (task_36):

1. Отборы стоят в параметрах виртуальных таблиц, а не фильтром СКД поверх всего?
2. Агрегация выполнена в запросе, а не компоновщиком по детальным строкам?
3. В наборе нет полей «на всякий случай» (каждое поле — чтение на строку)?
4. Виртуальная таблица не вызывается внутри соединений без отборов (task_26)?
5. Промежуточные наборы переиспользуются временными таблицами с индексами?
6. План запроса посмотрен на боевом объёме, а не на трёх тестовых записях?
7. Результат после оптимизации сверен с эталоном (оптимизация не меняет цифры)?

## 7. Безопасность (task_9, task_133–138)

- новый объект — сразу роль и права; «полные права» запрещены;
- секреты вне кода и вне репозитория;
- ПДн в логах и отчётах маскируются через единый модуль.
- Логирование (task_50): ключевые события (проведение, загрузки, ошибки
  обменов, вход пользователей) пишутся только через РИХ_Логирование
  JSON-форматом. Обязательно: вид события, объект, итог/числа, ID инцидента
  у ошибок. Никогда: пароли, токены, полные ПДн (телефоны, паспорта) —
  маскирование исполняет модуль, а не вызывающий код.

## 8. Git и артефакты (task_3)

- бинарные артефакты (.cf/.cfu/.dt) — только в `internship/build/` (в .gitignore);

## 9. БСП или своё решение (task_8)

- В типовых конфигурациях (БП, ДО, УТ) используем механизмы БСП штатными
  подключениями. Код БСП в свою конфигурацию кусками не копируем: копия
  перестаёт обновляться и расходится с оригиналом.
- В своей конфигурации (БСП нет) механизм пишем сами, если он нужен точечно,
  а тащить всю библиотеку нецелесообразно: учебный пример — версионирование
  `РИХ_ИсторияИзменений` (регистр + подписка ПриЗаписи + снимок XML).
- Свой аналог обязан повторять модель данных оригинала (версия = неизменяемый
  снимок + автор + дата + порядковый номер внутри объекта), а не только идею.

## 11. Деньги и округление (task_16)

- Деньги — `Число(15,2)`, округлять до 2 знаков; количество — до 3.
  Правило одно на проект: никаких «округлю, как в этом месте получилось».
- Суммы денег не сравнивают оператором «=» после делений и процентов:
  сравнивают с допуском в копейку (`|А − Б| ≤ 0.01`) или через `Окр`.
- Распределение суммы по строкам — только `РаспределитьСумму` из
  РИХ_ОбщегоНазначения: остаток получает часть с наибольшим весом
  (при равных весах — первая из них); наивное округление каждой части
  теряет копейку и запрещено.
- НДС: с налогом `С × (100 + Ставка) / 100`; выделить налог из суммы
  с налогом — `С × Ставка / (100 + Ставка)`. Округляется результат
  каждой операции, не только итог документа.

## 12. Что блокирует PR (task_12)

- ошибки статического анализа категорий «Ошибка» и «Важное»;
- прогон базового контура (lint_bsl.py по исходникам) обязателен локально
  и в CI по PR (GitHub Actions, job L0): 0.04 с на текущем объёме —
  проверка, которую не запускают, привычкой не становится;
- ложные срабатывания не отключают правило целиком: чинится инструмент
  или помечается конкретное место с обоснованием (пример — R001, task_8/12);
- незакрытые замечания code review уровня Critical/Major;
- отсутствие тестов на новую расчётную логику;
- незаполненная рефлексия.

## 13. Локализация (task_40)

- Новый объект метаданных — синонимы RU и EN в день создания объекта,
  а не «когда попросит переводчик».
- Пользовательские строки (сообщения, заголовки) не вшиваются в код
  на одном языке: НСтр или синонимы метаданных.
- Многоязычные данные — регистром по языкам (ADR task_40), не колонками
  НаименованиеEN/DE: язык добавляется данными, не релизом.
- Отсутствие перевода — fallback на базовое наименование, а не пустота.
- Даты/числа в строках для пользователя — форматом локали, в машинных
  контрактах — только ISO 8601/UTC (task_15/17).

## 14. Расширения (task_48)

- Доработка обязана быть расширением, если она: локальна для одной
  площадки/заказчика; является дополнительным контролем поверх базовой
  логики; должна отключаться без релиза основной конфигурации.
- В основную конфигурацию идёт поведение, обязательное для всех установок
  (движения, контроль остатков, RLS): расширение не должно быть
  единственным носителем учёной истины.
- Расширение не меняет типы и состав реквизитов основной конфигурации;
  отключение расширения не ломает данные (проверяется при сдаче).

## 15. Форматы обменов (task_75)

JSON — по умолчанию для REST-интеграций RIH: компактнее (поступление
361 байт против 590 у XML на том же документе), нативно читается
партнёрами-магазином и лояльностью. XML — где его требует партнёр
или стандарт формата: банк и ЭДО-подобные пакеты, CommercialXML-подобные
обмены, XDTO-схемы с жёсткой валидацией. Сериализация — только
РИХ_Форматы на штатных ЗаписьJSON/ЧтениеJSON: ручная склейка строк
JSON/XML запрещена (спецсимволы ломают payload молча). Даты в обменах —
ISO 8601, Null передаётся явно, а не отсутствием поля.

## 16. Таймауты внешних вызовов (task_127)

- Внешний вызов без явного таймаута запрещён. Таймаут «по умолчанию»
  платформы политикой не является; значение — в коде вызова и в
  таблице documentation/integrations/timeouts.md одновременно.
- Значение обосновывается замером p95 под нагрузкой с запасом на
  деградацию партнёра; один таймаут «30 секунд на всё» запрещён.
- Таймаут означает «статус неизвестен», а не «не выполнилось».
  Неидемпотентная операция после таймаута не повторяется слепо:
  статус выясняется запросом к партнёру или повтором тем же ключом
  идемпотентности. Платёж новым ключом после таймаута запрещён.
- Вызов партнёра внутри транзакции запрещён (task_44): таймаут там
  держит блокировки дольше самой операции.

## 17. Повторные попытки (task_128)

- Повторы выполняет РИХ_ПовторныеПопытки, а не участки клиентов:
  политика по умолчанию — 3 попытки, база 1 с, множитель 2,
  потолок задержки 30 с, общий бюджет 60 с. Копипаста политики
  по клиентам запрещена.
- Повторяются только временные исходы: 408, 429 (с уважением
  Retry-After вызывающим контуром), 500, 502, 503, 504, сеть и
  таймаут. Ответы 400/401/403/404/409/422 возвращаются с первой
  попытки: повторять свою ошибку бессмысленно.
- Предусловие повтора — идемпотентность операции или её ключ
  у партнёра (task_105). Небезопасная операция без ключа не
  повторяется автоматически.
- Каждая попытка пишется в ЖурналИнтеграций с номером попытки:
  серия повторов видна в мониторинге до звонка партнёра.
- Повтор внутри транзакции запрещён; что может подождать минуту —
  очередь (task_95/110), а не синхронный ретрай.
