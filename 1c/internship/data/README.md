# Учебные данные

Файлы, которые задания просят прочитать, разобрать и загрузить. Это **не** боевые
данные и не дамп системы: наборы собраны так, чтобы на них было видно типовые
проблемы разбора — кавычки, разделители внутри значений, кодировки, дубли,
нераспознанные строки.

| Файл | Для чего | Задания |
|---|---|---|
| `nomenclature_sample.csv` | номенклатура: 20 строк с «коварными» значениями | task_17, task_55 |
| `sales_plan_sample.csv` | план продаж по магазинам и периодам | task_35 |
| `bank_statement_sample.txt` | банковская выписка в формате обмена `1CClientBankExchange` | task_118 |
| `commerceml_sample.xml` | упрощённый CommerceML: каталог, цены, остатки | task_89 |
| `supplier_price/` | рабочая область файлового обмена прайс-листами | task_88 |

## Правила

1. **Данные не меняются в процессе задания.** Если для проверки нужен «сломанный»
   файл, создайте копию в `internship/build/` — каталог вне Git.
2. **Файлы не содержат персональных данных.** Всё совпадение с реальными людьми
   и компаниями вымышлено; ФИО, телефоны и адреса в наборы не добавляйте (task_135).
3. **Ожидаемый результат разбора описан** в заголовке каждого набора или в
   `supplier_price/README.md`: иначе непонятно, правильно ли вы прочитали файл.
4. **Новый набор данных — с описанием формата**: разделитель, кодировка, обязательные
   поля, что считать ошибкой строки.
5. Большие объёмы (10 000 позиций для замера task_89) **генерируются скриптом**,
   а не хранятся в Git: `src/scripts/seed_demo_data.py`.

|---|---|---|---|
| `nomenclature_sample.csv` | UTF-8 | `;` | реальные файлы поставщиков часто Windows-1251 — проверяйте на их файлах |
| `sales_plan_sample.csv` | UTF-8 | `;` | |
| `bank_statement_sample.txt` | UTF-8 | `=` | формат «ключ=значение» |
| `commerceml_sample.xml` | UTF-8 | — | объявление кодировки обязательно |

## Что должно получиться при разборе (самопроверка)

Наборы собраны так, чтобы результат разбора можно было сверить с числом, а не
«на глаз». Если ваши цифры другие — ошибка в разборе, а не в данных.

### `nomenclature_sample.csv`

* 20 записей в 21 физической строке: последняя запись содержит перевод строки
  внутри значения в кавычках;
* 10 колонок, разделитель `;`;
* ошибок данных намеренно три: `SKU-00018` (цена `-1.00`), `SKU-00019` (пустые
  `group` и `barcode`), `SKU-00020` (перевод строки в `name`);
* весовых позиций (`is_weight=true`) — две: `SKU-00004`, `SKU-00013`;
* сумма цен по всем 20 позициям — 124.97 (включая намеренно неверную `-1.00`).

### `sales_plan_sample.csv`

* 18 записей, 8 колонок;
* общая сумма `planned_amount` — 66854.50;
* три учебных сценария для отчёта «план-факт» (task_35):
  * `M005` в ноябре имеет план версии 2 с нулём — «плана нет» при формально
    существующей строке;
  * `M005` в декабре план есть, факта в оперативной базе не будет — «факта нет»;
  * `SKU-99999` — товар, которого нет в номенклатуре: связь наборов не должна
    ни потерять строку, ни задвоить сумму факта.

### `bank_statement_sample.txt`

* 6 записей документов: 3 входящих платежа и 3 списания;
* списание `Номер=000077` встречается **дважды** — это дубль, который корректная
  загрузка обязана отсечь (идемпотентность, task_118);
* входящих: 2434.30; списаний без дубля: 6740.55 (с дублем было бы 11740.55);
* остаток: начальный 15430.15, конечный 11123.90 — как в секции `СекцияРасчСчет`.
  Если после загрузки получилось 6123.90, платёж применился дважды;
* один платёж не распознаётся автоматически: `Номер=000144`, назначение
  «Возврат денежных средств по претензии без номера документа» — он должен попасть
  в список ручного разбора.

### `commerceml_sample.xml`

* 6 товаров (атрибут `СодержитТовары="6"` совпадает с фактом), 5 предложений,
  3 группы (одна вложенная: «Напитки» → родитель «Бакалея»);
* товар `SKU-00020` есть в каталоге, но **нет в предложениях** — цена и остаток
  не придут: случай «товар без цены»;
* товар `SKU-00018` имеет цену `-1.00` — ошибка данных;
* товар `SKU-00004` весовой (`<Весовой>true</Весовой>`), остаток дробный (85.500);
* у товара `SKU-00011` количество 0 — нулевой остаток, а не отсутствие данных;
* для режима «только изменения» используйте `ДатаИзменения`: после
  2026-11-10T00:00 изменены две позиции — `SKU-00004` (15.11) и `SKU-00020`
  (10.11 15:05), поэтому дельта обязана содержать ровно две записи.

### `supplier_price/samples/`

* `prices_supplier_001_2026-11-17.csv`: 12 строк, 1316 байт, сумма в `.ctl`
  совпадает с файлом — корректный обмен;
* `prices_supplier_002_broken.csv`: 6 строк данных, из них валидны 3
  (`SKU-00001`, `SKU-00008` — с неверным форматом даты `18.11.2026`,
  `SKU-00009`); ошибки: пустой `sku`, отрицательная цена, нечисловая цена,
  дата не ISO 8601. Control-файл намеренно заявляет `rows=4` — расхождение
  с фактическими 6 строками должно быть обнаружено **до** загрузки;
* `prices_supplier_003_truncated.csv`: обрыв записи — незакрытая кавычка и
  обрезанная последняя строка. Загрузка наполовину недопустима.
