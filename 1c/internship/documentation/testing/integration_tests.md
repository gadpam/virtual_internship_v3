# Интеграционные тесты Q2 (task_141)

## Что гоняется

`checks_integration.py` — 11 тестов против живых mock стенда
(магазин :8026, лояльность :8021, ТК :8022, банк SOAP :8023):
каталог, заказ и его дубль, начисление/списание/сторно лояльности,
расчёт и заявка ТК, курсы и идемпотентный платёж банка. Негативы:
500 партнёра, медленный ответ против клиентского таймаута, мусор
вместо JSON по контракту, повтор после 500 без двойного начисления.

Проверяется поведение, а не «не упало»: дубль — это duplicate/409
по ключу идемпотентности, 500 — повтор той же операцией ровно
один раз, мусор — отлов проверкой формы (урок task_132: валидный
JSON без нужных полей — тоже мусор).

## Изоляция и стабильность

Каждый тест заводит свои данные (идентификаторы с уникальным
префиксом прогона) и убирает за собой: сторно лояльности, reset
ТК. Уникальность — на прогон, не на процесс: общий префикс на
три прогона подряд ловил дубли первого и «плавал» на ровном
месте — найдено и исправлено в этом задании. Итог: 3 прогона
подряд зелёны, ~1 с каждый (бюджет контура — до 10 минут).

## Где запускается и почему не в PR-CI

PR-CI GitHub не имеет ни mock-сервисов, ни опубликованной ИБ
(платформы 1С в CI нет по лицензиям — контур task_64): вечно
красный шаг хуже честного пропуска. Поэтому:

- PR-CI: контракты (task_140) и сканеры — то, что выполнимо везде.
- Локальный/ночной стенд: checks_integration против поднятых
  моков одной командой стенда (task_139); падение сначала
  отвечает «чей стенд» — наш, мока или контракт (task_140),
  недоступность партнёра — отдельный статус, а не «красный код».

Плавающий тест чинится в тот же день: команда, привыкшая
игнорировать красное, не заметит и настоящее падение.
