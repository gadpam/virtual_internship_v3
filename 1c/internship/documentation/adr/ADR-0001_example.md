# ADR-0001: Текстовые исходники 1C:EDT в Git вместо бинарных `.cf`

* **Участники:** наставник, владелец интеграции
* **Задания:** task_64, task_65, task_265
* **Связанные ADR:** —

> Это пример оформления. Замените содержание на своё первое реальное решение.

## Контекст

Проект RIH ведётся одним разработчиком, но к середине года к нему подключаются
мобильный контур, AI-сервис и BI. Нужно хранить историю изменений, видеть diff
в code review, собирать конфигурацию автоматически и воспроизводить релиз.

Бинарный `.cf` в Git даёт историю файлов, но не даёт ответа на вопросы «что
именно изменилось» и «кто это изменил и зачем». Ручная выгрузка `.cf` в репозиторий
также делает невозможной автоматическую сборку в CI.

## Решение

Ведём разработку в 1C:EDT, храним в Git **текстовое представление** конфигурации
(каталог `internship/Configuration/src`), а бинарные артефакты (`.cf`, `.epf`)
собираем в CI и кладём в `internship/build/` — вне контроля версий.

## Рассматриваемые альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| `.cf` в Git | привычно, не нужен EDT | diff нечитаем, code review невозможен, сборка ручная | не даёт инженерного процесса |
| Хранилище конфигурации 1С | штатный механизм, история захвата | нет diff в PR, нет CI, привязка к одному серверу | не совмещается с code review в Git |
| **EDT + Git** | текстовый diff, CI, ревью, воспроизводимость | нужен EDT, дисциплина в структуре проекта | **выбрано** |

## Последствия

### Положительные
* code review по реальному diff (task_54, task_145);
* автоматическая сборка артефактов и манифест с контрольными суммами (task_265);
* история изменений привязана к заданиям и коммитам;
* новый участник поднимает проект одной командой (task_264).

### Отрицательные
* требуется 1C:EDT и знания его структуры проекта;
* часть операций (внешние обработки, расширения) удобнее делать в Конфигураторе —
  нужен регламент, что где правится;
* бинарные артефакты в Git не хранятся: нужен CI, чтобы их получить.

### Цена
* настройка CI: ~1 день; обучение EDT: ~3 дня; регламент структуры: ~2 часа.

## Как проверить, что решение работает

* любой change request проходит ревью по diff до merge;
* артефакт релиза собирается конвейером и проходит `check_artifacts.py`;
* новый стенд разворачивается из репозитория без ручных шагов.

## Условия пересмотра

* смена платформы на версию, где EDT-экспорт теряет метаданные;
* появление требования работать без Git (например, изолированный контур заказчика);
* рост команды до состояния, где хранилище 1С становится обязательным по регламенту ИТ.
