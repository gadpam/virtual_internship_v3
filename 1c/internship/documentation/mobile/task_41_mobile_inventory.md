# task_41: мобильное место кладовщика — сценарий «Инвентаризация»

## Почему прототип — эмуляция, а не мобильное приложение

Мобильной платформы в стенде нет (ограничение среды с task_0). Риск
сценария — не экраны, а офлайн: данные устаревают, двое меняют одно,
связь рвётся посреди отправки. Поэтому прототипируется очередь
и синхронизация (src/scripts/mobile_offline_sim.py), экраны — по макету ниже.

## Что мобильная платформа умеет и чего нет (из документации)

Умеет: управляемые формы облегчённого вида, работу с локальной ИБ на
устройстве, камеру как сканер штрихкодов, обмен через HTTP-сервисы при
связи. Не умеет (или дорого): тяжёлые СКД-отчёты на устройстве, фоновую
работу без запуска приложения, полную конфигурацию «как на десктопе» —
мобильное приложение собирается отдельной конфигурацией под сценарий.

## Сценарий по шагам

1. Утром (по Wi-Fi склада) устройство тянет снимок: номенклатура,
   штрихкоды, остатки своего склада (только закреплённый склад — RLS task_9).
2. Кладовщик идёт по складу: скан штрихкода → карточка (учётный остаток
   скрыт до ввода факта, чтобы не подсказывать цифру) → ввод фактического
   количества → строка в локальную очередь инвентаризации.
3. Нет связи — не беда: очередь локальная, работа не останавливается.
4. При связи очередь уходит одним пакетом; сервер сверяет версии снимка.
5. Расхождения учёт/факт оформляются актом инвентаризации уже на сервере —
   устройство не «правит остатки» само никогда.

## Объём данных на устройстве (посчитано симуляцией)

| Набор | Строк | Вес |
|---|---|---|
| Номенклатура (~220 байт/строка) | 100 000 | ~22 МБ |
| Штрихкоды (1.3 на товар) | 130 000 | ~8 МБ |
| Остатки активных пар склад×товар | 40 000 | ~2 МБ |
| **Итого снимок** | | **~32 МБ** |

Вывод: полный каталог на устройство влезает, но тянуть его весь незачем:
номенклатуру — по своему складу и активным товарам, картинки не тянем.

## Синхронизация и 3 конфликтные ситуации

1. **Снимок устарел** (на сервере было поступление, пока считали):
   версия снимка младше серверной — факт не перезаписывает учёт;
   расхождение уходит в акт, решает товаровед. (Симуляция: SKU-1.)
2. **Один товар изменили двое** (два устройства, один склад): сервер
   принимает первый пакет; второй получает конфликт по версии пары
   и уходит в ручную сверку — «последний записал» запрещено: молчаливая
   перезапись факта — это фальсификация инвентаризации.
3. **Пакет ушёл частично** (связь умерла на середине): каждая операция
   очереди имеет идемпотентный ключ (устройство+номер операции); повторная
   отправка не плодит дублей — сервер отвечает «уже применено».
   (Механика идемпотентности — та же, что в HTTP-интеграциях Q2.)

Правило общее: устройство предлагает факт, сервер владеет учётом;
конфликт — это данные для решения человека, а не ошибка синхронизации.
