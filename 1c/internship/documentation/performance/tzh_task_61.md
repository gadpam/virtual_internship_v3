# task_61: технологический журнал — настройка и чтение

## Честная граница среды

Платформы 1С в среде нет, поэтому ТЖ кластера не пишет. Сделано две вещи:
готовый `logcfg.xml` для стенда с платформой (события CALL/EXCP, TLOCK
и DBPOSTGRES дольше 1 с, поля контекста — рядом: `logcfg_example.xml`)
и эквивалентный журнал на стенде: серверный порог PostgreSQL
(`log_min_duration_statement`) недоступен без суперпользователя, поэтому
журналом событий работают замеры РИХ_Профилирование/базлайн и клиентские
прогоны sprint_10 — у каждого события есть операция, длительность,
контекст объёма и сессия-прогон. Методика чтения та же: отбираем
длительные, группируем по операциям, ищем причину по контексту.

## Топ-5 длительных событий стенда (по замерам sprint_10)

| # | Событие (аналог DBPOSTGRES/CALL) | Длительность | Контекст | Предполагаемая причина |
|---|---|---|---|---|
| 1 | Загрузка движений пакетом 100 | 5 212 мс / 100 тыс. | lab55, 1 000 транзакций | Транзакция на 100 строк: фиксаций больше, чем работы |
| 2 | Вставка 100 тыс. при живом индексе | 443 мс | lab55.movements | Цена индекса (warehouse, product) на записи |
| 3 | Отчёт остатков по складам | 181 мс | 1 млн движений | Полный агрегат без среза — ожидаемо, не дефект |
| 4 | Вставка 100 тыс. без индекса | 114 мс | lab55 | Базовая запись для сравнения со строкой 2 |
| 5 | Остаток пары без индекса | 52.2 мс | 1 млн, Seq Scan | Не было составного индекса под срез |

## Оптимизация, подтверждённая журналом

Событие №1: размер пакета загрузки 100 → 1000 (РИХ_ПакетнаяОбработка,
task_57). Повторный «журнал» замеров: 5 212 → 541 мс на тех же 100 тыс.
строк, ускорение ×9.6, цена — откат пакета из 1000 при сбое вместо 100.
Событие №5 тем же способом подтверждено индексом: 52.2 → 0.13 мс
(task_58). В ТЖ платформы обе оптимизации проверяются отбором DBPOSTGRES
по длительности после релиза.
