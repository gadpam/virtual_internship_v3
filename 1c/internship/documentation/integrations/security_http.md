# Аутентификация HTTP-сервиса и мини-аудит (task_81)

## Как устроено

Ключ партнёра в заголовке `X-Api-Key`; в базе (РС КлючиДоступаИнтеграций)
лежит только его SHA-256 хеш — утечка базы рабочего ключа не даёт.
Неудачные попытки пишутся в ЖурналИнтеграций со статусом 401; 5 неудач
за 10 минут с одного адреса — блокировка на 15 минут (ответ 429).
Технический пользователь сервиса — роль РИХ_ИнтеграционныйСервис
(есть в конфигурации с task_9): ключ без права на документы получит
403 на их маршрутах при живой ИБ. В логи ключ не попадает никогда:
журнал пишет сервис, операцию и результат, не заголовки (task_50).

## 10 угроз и меры

| # | Угроза | Мера |
|---|---|---|
| 1 | Подбор ключа перебором | Блокировка 5/10 мин → 15 мин, журнал попыток |
| 2 | Утечка ключа из репозитория | Ключей в Git нет: учебный ключ mock — не наш ключ; боевые — секреты окружения (task_134) |
| 3 | Утечка базы ключей | В базе только SHA-256 хеши |
| 4 | Повтор запроса (replay) с созданием дубля | Idempotency-Key + уникальность внешнего ид заказа |
| 5 | Подмена payload по дороге | HTTPS на внешнем контуре (nginx TLS), внутри — доверенная сеть стенда |
| 6 | Инъекция через поля заказа | Параметризованные запросы, валидация типов до логики (стандарт §3) |
| 7 | Стек и детали ошибки наружу | Единый формат: короткий message + incidentId, стек только в журнале |
| 8 | ПДн покупателя в логах | customer_ref маскируется политикой логирования (task_50/135) |
| 9 | DoS тяжёлыми запросами каталога | Лимит пагинации 500, 429 при переборе, nginx-лимиты стенда |
| 10 | Отозванный ключ партнёра продолжает работать | Активен=Ложь в регистре ключей — доступ закрыт без релиза |

Прогон против mock подтвердил базовую семантику: без ключа 401,
с неверным — 403, блокировка и ротация реализуются нашей стороной
(РИХ_Интеграции.КлючДопустим) и проверяются зеркально до живой ИБ.
