# КД 2, КД 3 или свой код: сравнение и правило проекта (task_102)

| Критерий | КД 2.0 (универсальный XML) | КД 3.0 (EnterpriseData/XDTO) | Свой код контура |
|---|---|---|---|
| Строгость контракта | Слабая: XML по правилам, схема не валидирует жёстко | Сильная: XDTO-схема проверяется фабрикой на границе | Как спроектируем: у нас — XDTO-пакет и контракт-тесты |
| Отладка | Протокол и файлы; точек останова нет | Сообщения читаются как XDTO-объекты, отладка ближе к коду | Полная: обычный код в репозитории |
| Производительность | Самая низкая: универсальный XML тяжёл | Средняя: XDTO-объекты дороже структур, дешевле универсального XML | Самая высокая на наших объёмах (пакеты task_91/117) |
| Работа с типовыми | Готовые правила у типовых — главный козырь | Типовые отдают EnterpriseData из коробки | Правила типовых не переиспользуются |
| Порог входа | Низкий для «поле в поле», резко растёт на логике | Средний: надо понимать XDTO и схему | Низкий внутри нашей команды, высокий для чужих |
| Поддержка | КД 2 на ИТС, развитие заморожено в пользу КД 3 | Развиваемый стандарт типовых конфигураций | Наша ответственность целиком |

## Правило проекта

- Обмен с типовыми конфигурациями (БП, ДО в Q3) — КД 3/EnterpriseData:
  типовые говорят на нём из коробки, изобретать второй язык глупо.
- Регулярные обмены нашего контура (магазин, лояльность, ТК, филиал)
  — свой код и контрактные тесты: объёмы и идемпотентность наши,
  готовых правил не существует.
- КД 2 — только разовые миграции и наследие: новые обмены на ней
  не начинаем (поддержка заморожена, правила не читаются в git).

Сообщение EnterpriseData-стиля собрано кодом в РИХ_XDTO
(СообщениеКаталогаEnterpriseData): заголовок отправитель/получатель,
тело — объектами пакета. При появлении КД 3 правила заменят сборку,
структура сообщения при этом не изменится.
