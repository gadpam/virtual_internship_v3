# ЭДО: поток, требования к оператору и риски (task_90)

## Схема потока

```
Поставщик ──УПД (XML ФНС)──► Оператор ЭДО ──► Приёмник RIH (РИХ_ЭДО)
                                                   │ проверка подписи (task_115)
                                                   ▼
                                              Документ учёта ──► БП (вычет НДС)
Статусы (получен/подписан/отклонён/аннулирован) идут обратным ходом
через оператора; каждый переход пишется в ЖурналИнтеграций.
```

## Требования к интеграции с оператором (10)

1. API приёма и отдачи документов с идемпотентными ключами (ИдДокумента).
2. Форматы ФНС (УПД, счёт-фактура) с версиями схем и сроком поддержки старых.
3. Проверка УКЭП: сертификат, срок действия, цепочка доверия, отзыв.
4. Статусы доставки и подписания с квитанциями оператора.
5. Хранение оригиналов XML и подписей неизменно (юридическая значимость).
6. Аудит: кто/когда принял, подписал, отклонил — в нашем журнале.
7. SLA оператора и поведение при его недоступности (очередь, а не потеря).
8. Роуминг между операторами для контрагентов другого оператора.
9. Аннулирование и корректировки как отдельные документы, не правки принятых.
10. Тестовый контур оператора, совпадающий по схемам с боевым.

## Риски и меры (4)

| Риск | Мера |
|---|---|
| Отзыв/аннулирование принятого документа | Статус аннулирован запрещает проведение; сторно в учёте отдельным документом |
| Дубль доставки оператором | Идемпотентность по ИдДокумента: повтор — 200 duplicate без второго документа |
| Ошибка/подделка подписи | Проверка УКЭП до сохранения; битая подпись — отказ приёма и инцидент, а не «принять и разобраться» |
| Оператор недоступен | Исходящие — очередь с повтором; входящие оператор хранит до восстановления (требование 7) |

Приёмник-заглушка (HTTP-сервис РИХ_ЭДО): XML принимается, дубль по
X-Document-Id отсекается по журналу, вызов пишется в ЖурналИнтеграций.
Проверка подписи и статусы ФНС — task_115 на этом же договоре.
