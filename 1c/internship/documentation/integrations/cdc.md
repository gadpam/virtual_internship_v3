# CDC: как RIH получает только изменения (task_123)

Сравнение способов, выбор и замер. Цифры — стенд PostgreSQL,
`src/scripts/checks_cdc.py`: источник 100 000 строк продаж.

## Четыре способа получения изменений

| Критерий | Дата изменения / версия | План обмена (регистрация) | Журнал регистрации | Триггеры СУБД |
|---|---|---|---|---|
| Что ловит | изменённые объекты с полем даты | всё зарегистрированное для узла, включая удаления | события «записали/удалили» без состава изменений | всё на уровне строк таблиц |
| Удаления | не видит вообще | видит (регистрация удаления) | видит факт, без данных объекта | видит |
| Заднее число | умирает: период уже выгружен, дата документа старая | бизнес-дата в регистрации сохраняется | дата события есть, бизнес-даты нет | бизнес-дата в строке есть |
| Цена | дёшево, но дыряво | штатно, номера сообщений и подтверждение | дёшево, но структуру изменений строить самим | мощно, но вне метаданных 1С |
| Поддерживаемость | поле есть не везде | штатный механизм платформы | ручной разбор лога | ломается при обновлении конфигурации и смене структуры таблиц |

## Выбор

Для **фактов продаж витрины**: подписка на запись/удаление чека пишет
бизнес-день чека в РС ОчередьПересчётаВитрины той же транзакцией;
часовая обработка пересчитывает затронутые дни полной перезаписью
(task_122). Это регистрация изменений по смыслу плана обмена,
только единицей изменения выбран день агрегата, а не строка чека:
заднее число лечится конструкцией (день марта пересчитается в апреле),
удаление — tombstone подписки «перед удалением» плюс перезапись дня.

Для **НСИ и справочников**: регистрация изменений плана обмена
(РИХ_Обмены, task_97) — штатно, с удалениями и подтверждением номера.

Отклонено: дата изменения (не видит удалений и заднего числа),
журнал регистрации (нет состава изменений), триггеры СУБД (живут
вне конфигурации и умирают при её обновлении молча).

HTTP-выгрузка дельты: `GET /api/v1/changes?since=` отдаёт изменённые
дни и их строки; полностью исчезнувший день потребитель удаляет
по списку `changedDays`. Неизменённое повторно не отдаётся.

## Проверки стенда

- Полная выгрузка: 100 000 строк источника, 8.3 МБ JSON; витрина
  зерна день×магазин×товар — 6 900 строк.
- Дельта суток: 3 000 изменений = 323 КБ — **в 25 раз меньше** полной;
  повторная дельта пуста.
- Заднее число: строка мартовского дня +500 в апреле; дельта
  подхватила день по журналу, витрина пересчитала, сверка сошлась
  (228345.00 → 228845.00).
- Физическое удаление: tombstone до удаления, пересчёт дня, призрака
  в витрине нет; итог дня равен источнику.
- Простой потребителя: дельта со старого номера догнала 500 изменений
  трёх дней — журнал хранит изменения дольше окна простоя (у нас —
  до успешной обработки, очищается потребителем, а не по таймеру).

## Ответ на проверку понимания

Объект удалили физически: потребитель получит tombstone в ближайшей
дельте и удалит призрака при пересчёте дня — в течение часа
(расписание дельты). «Никогда» было бы ответом для дельты по дате
изменения: именно поэтому она не выбрана.
