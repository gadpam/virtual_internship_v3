# Размышление по заданию task_060

**Задание:** Кеширование, повторные вызовы и «дорогие» справочные данные
**Дата:** 2026-11-17
**Время:** план 3 ч / факт 1.5 ч

## Три риска устаревания и контроль

1. Писатель забыл сбросить: отчёт считает по старому порогу. Контроль —
   сброс живёт не «где-то», а обязателен в процедуре записи порогов;
   ревью проверяет пару «запись + СброситьКэш» как одно изменение.
2. Длинный сеанс живёт дольше изменения: пользователь открыл форму утром,
   порог поменяли в обед. Контроль — кэш только на сеанс и только для
   данных, где час устаревания не вредит решению (порог отчёта — да,
   остаток для проведения — никогда).
3. Кэш маскирует отсутствие данных: пустая таблица закэшировалась до
   загрузки порогов. Контроль — загрузка порогов заканчивается сбросом,
   а пустой кэш отличим в журнале по первому чтению сеанса.

Обнаружить устаревание помогает сверка выборочных чтений с базой
(у нас — assert зеркала: значения кэша равны базе по всем парам).

## Ошибка, которую я больше не повторю

Кэшировать «для скорости» без сценария инвалидации: первый же замер
показал кэш, честно врущий 500 вместо 900, — скорость лжи не нужна.
