# Как платформа хранит данные в СУБД (task_181, контур PostgreSQL)

Серверной базы MS SQL в среде нет (план Q3, task_150): спринты
31–32 выполняются на PostgreSQL аналогами, расхождения фиксируются
здесь. Имена физических таблиц платформой навсегда не обещаются:
прямой SQL по ним — долг к обновлению платформы (task_287).

## Отображение «объект → таблица»

| Объект RIH | Физическая таблица (стиль платформы) | Что внутри |
|---|---|---|
| Справочник Номенклатура | `_Reference<id>` | код, наименование, ссылка-ключ, реквизиты колонками с префиксами |
| Документ ПоступлениеТоваров | `_Document<id>` + `_Document<id>_Goods` (табличная часть) | шапка одной таблицей, строки — отдельной, со ссылкой на владельца и номером строки |
| Регистр накопления ТоварыНаСкладах | `_AccumRg<id>` (+ таблицы итогов) | движения строками: период, регистратор, вид движения, измерения, ресурсы |
| Регистр сведений | `_InfoRg<id>` | записи с периодом и измерениями |
| Ссылка | составной ключ с типом объекта | не «красивый код»: соединение по ссылке — преобразование, известное платформе |

## Виртуальных таблиц в СУБД нет

Остатки, обороты и срезы вычисляются запросами платформы поверх
сырых движений и итогов: «готовой цифры остатка» в таблице
движений нет. Строить отчёт по сырым таблицам в обход платформы —
переизобрести итоги с ошибками; контрольный приём — сверка
агрегации движений с виртуальной таблицей (зеркало задания).

## Правила контура

- Читать сырые таблицы — диагностика («что реально записано»).
- Писать SQL-ом в обход платформы запрещено: кэши, регистрация
  изменений, индексы и версионирование останутся в неведении,
  база станет несогласованной.
- Номера таблиц берутся из системных каталогов/конфигурации,
  а не угадываются по порядку создания.
