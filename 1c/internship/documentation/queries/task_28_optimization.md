# task_28: запрос оборотов по группам через временные таблицы

Исходный запрос — task_27 (соединение движений со справочником и
группировка одним запросом). Переписан пакетом через менеджер временных
таблиц (менеджер — чтобы таблицы жили между запросами пакета и падали
вместе с ним):

```bslq
ВЫБРАТЬ
	Номенклатура.Ссылка КАК Товар,
	Номенклатура.Группа КАК Группа
ПОМЕСТИТЬ ВтТоварыГрупп
ИЗ
	Справочник.Номенклатура КАК Номенклатура
ГДЕ
	Номенклатура.Группа В ИЕРАРХИИ (&Группы)
;
ИНДЕКСИРОВАТЬ ПО
	Товар
;
////////////////////////////////////////////////////////////////////////////////
ВЫБРАТЬ
	Товары.Группа КАК Группа,
	СУММА(Обороты.КоличествоОборот) КАК Оборот
ИЗ
	ВтТоварыГрупп КАК Товары
		ВНУТРЕННЕЕ СОЕДИНЕНИЕ РегистрНакопления.ТоварыНаСкладах.Обороты(
				&НачалоПериода, &КонецПериода, , ) КАК Обороты
		ПО Обороты.Номенклатура = Товары.Товар
СГРУППИРОВАТЬ ПО
	Товары.Группа
```

## Индексы: почему эти поля

- `ВтТоварыГрупп(Товар)` — по полю соединения со стороны временной таблицы:
  соединение Обороты→ВТ ищет товар в ВТ, индекс делает это без перебора.
- В финальном запросе индекс по Группе не создаю: таблица ВтТоварыГрупп
  маленькая (товары двух групп), а группировка и так идёт по ней.
  Индекс «на всякий случай» стоит записи и памяти: индекс нужен
  под конкретное соединение или отбор.

## Замер (PostgreSQL-аналог labq, 100 001 движение)

| Вариант | Время |
|---|---|
| Исходный одним запросом | 47–84 мс (разброс прогонов) |
| Пайплайн с вт целиком (создание+индексы+финал) | 58.9 мс |
| Финальный запрос по готовым вт | 0.21 мс |

Наборы результатов сверены — совпадают полностью. Вывод честный:
на одиночном запросе временные таблицы не ускорили (58.9 ≈ исходный
в пределах разброса) — они окупаются, когда промежуточный результат
используют несколько запросов пакета (task_26: соединение 0.31 мс по
готовой таблице) или когда платформа СУБД не может построить хороший
план для одного большого запроса.

## Когда временные таблицы НЕ нужны

- Одиночный запрос, где виртуальная таблица и есть весь запрос
  (простой отчёт по остаткам): материализация добавит запись и чтение.
- Маленькие объёмы и справочные отборы: накладные расходы пакета
  (создание таблиц, ИНДЕКСИРОВАТЬ) больше выигрыша.
- Когда промежуточный набор используется ровно один раз и СУБД строит
  нормальный план без него — проверяем планом, а не привычкой.
